### nv27_rw_duplex — NVLink4 链路确认全双工：双向对打 730.9 GB/s = 单向 1.97×，两方向完全对称（差 0.2%）

**假设**

NVLink 每条 link 由两组独立的差分对构成，理论上收发两个物理方向可以同时满速。若成立，则「GPU0 写 GPU1 的同时 GPU1 写 GPU0」的总带宽应接近单向的 2 倍；而「GPU0 同时读写 GPU1」由于**读请求本身要占用发出方向**，不应达到 2 倍。

**方法**

- 三个场景分开测，每个 kernel 跑满 >=50ms（256MB buffer × REP=12 = 3.2GB 逻辑字节）：
  - (a) GPU0 只写 / 只读 / 同时读写 GPU1。读写打 GPU1 上**两块不相交** buffer，避免读到刚写的数据命中 L2。
  - (b) 双向对打：GPU0 写 GPU1 与 GPU1 写 GPU0 同时进行。**每个 device 用自己的 stream 和自己的 event**，先都 launch 出去再统一同步，单流带宽用各自 event 算。
  - (c) 读写比例扫描：单 kernel 内按 `blockIdx` 分角色，写 block 和读 block 各自 grid-stride 遍历，总逻辑字节固定，因此各比例之间直接可比。
- 读侧 grid 开满 `4×SM=312 block`。这一点很关键：nv26 已证明 LOAD 受 outstanding 请求数限制，若给读只分一半 SM，读带宽会被并发度而非链路卡住，从而**低估双工总和**。
- 全程用 `nvl_read_counters(0)` 从 GPU0 视角核对 Tx/Rx 方向的实际字节分配，作为"两个物理方向确实同时在跑"的独立证据。

**实测数据**

(a) 单向 vs 同时读写：

| 场景 | 写 GB/s | 读 GB/s | 总 GB/s | 相对单向 |
|---|---|---|---|---|
| 只写 GPU0→GPU1 | 370.6 | - | 370.6 | 1.00x |
| 只读 GPU0←GPU1 | - | 369.1 | 369.1 | 1.00x |
| 同时读+写 | 349.3 | 243.8 | 487.6 | **1.32x** |

(a2) 硬件计数器方向验证（GPU0 视角，payload 为逻辑字节）：

| 场景 | dataTx (MB) | dataRx (MB) | rawTx (MB) | rawRx (MB) | raw/data |
|---|---|---|---|---|---|
| 只写 | 6442.5 | 0.0 | 7297.7 | 5840.5 | 2.039 |
| 只读 | 0.0 | 6442.5 | 4820.6 | 7269.1 | 1.877 |
| 同时读写 | 6442.5 | 6442.5 | 10315.4 | 11164.0 | 1.667 |

(b) **双向对打**：

| 场景 | 0→1 GB/s | 1→0 GB/s | 总 GB/s | 相对单向 |
|---|---|---|---|---|
| 单向 0→1 | 370.6 | - | 370.6 | 1.00x |
| 双向对打 | 365.4 | 366.3 | **730.9** | **1.97x** |

方向公平性：`|0→1 − 1→0| / 均值 = 0.2%`

(c) 读写比例扫描（总搬运字节固定 3221 MB）：

| 写占比 | 写 block | 读 block | 总有效 GB/s | vs 纯写 |
|---|---|---|---|---|
| 0% | 0 | 312 | 368.8 | 0.99x |
| 25% | 78 | 234 | 447.9 | 1.21x |
| 50% | 156 | 156 | **451.4** | **1.22x** |
| 75% | 234 | 78 | 395.2 | 1.07x |
| 100% | 312 | 0 | 371.1 | 1.00x |

(c2) 50/50 混合方向分配：dataTx=3222.0 MB，dataRx=3220.4 MB（**1.0005:1**，精确对半）。

**结论**

1. **NVLink4 链路是全双工，两个物理方向各自独立满速。** 依据 (b) 行"双向对打"：730.9 GB/s = 单向 370.6 的 **1.97×**，且两方向分别拿到 365.4 / 366.3 GB/s，**不对称度仅 0.2%**。这是本实验最干净的证据——两个方向各自跑到了单向满速的 98.6%，几乎没有互相损耗。

2. **单向注入上限 = 370 GB/s，双向聚合上限 = 731 GB/s。** 后者即每卡对单个 peer 的双工总容量。注意这远低于 18 link × 26.562 = 478 GB/s 的理论单向线速，说明瓶颈在 GPU 侧的注入/接收逻辑而非线路本身（370/478 = 77.4%，与 raw/data≈2.04 的协议开销方向一致）。

3. **「同时读写」只有 1.32× 而非 2×，是因为远端读要双向占用。** 依据 (a)：同时读写时写拿 349.3、读只拿 243.8。远端 load 的请求包必须从 GPU0 的 **Tx 方向发出**，数据才从 Rx 回来。所以读和写在 GPU0 的 Tx 方向上是**直接竞争**的，只有读的返回数据独占 Rx。这与 (b) 双向对打（两边都是纯写，各自只用自己的 Tx）形成对照，正好解释了 1.32× 与 1.97× 的差距。

4. **读写混合有正收益，最优点在 50/50 附近，为 451.4 GB/s（比纯写高 22%）。** 依据 (c) 表。混合能超过任何单向的 370，正是因为利用了空闲的反向带宽；但达不到 2× 也是因为读请求占用 Tx。75% 写时收益回落到 1.07×，因为读 block 太少，反向没吃满。**混合本身没有额外惩罚**——没有任何比例低于 0.99×。

5. **计数器证实两方向同时满载**：(a2) "同时读写"行 dataTx 和 dataRx **都是 6442.5 MB**，完全相等；(c2) 50/50 混合时 Tx/Rx = 3222.0/3220.4，比值 1.0005。方向字节分配与设计意图精确吻合，排除了"其实只走了一个方向"的可能。

6. **双工工作时协议效率反而变好**：raw/data 从只写的 2.039 降到同时读写的 **1.667**、50/50 混合的 1.685。原因是单向传输时反向链路仍要发 flow-control flit 和 ACK（只写场景 rawRx=5840 MB 而 dataRx=0，这 5.8GB 全是纯开销）；双向跑时这些控制流量可以**搭载（piggyback）在反向的数据包里**，摊薄了开销。

**不确定性**

- (a) 中"同时读写"的读带宽 243.8 GB/s 在三次重复间有一定波动（前一版 grid 减半时测得 218.9），因为读写两个 kernel 抢同一批 SM，调度比例不完全稳定。但写+读总和稳定在 437–488 区间，不影响"介于 1× 和 2× 之间且明显小于 2×"的结论。
- (c) 的比例是按 **block 数**划分而非按实际字节流量划分，由于读和写的单位效率不同（读受 outstanding 限制），"50% 写 block"不完全等于"50% 写字节"。c2 的计数器显示实际字节确实接近 1:1，说明这个近似在 50% 点上是成立的，但 25%/75% 点的实际字节比未单独核验。
- 只测了 GPU0↔GPU1 一对。虽然平台事实说明任意 GPU 对对称，但全双工特性未在其他对上复验。
- 未区分"18 条 link 每条都全双工"与"聚合层面表现为全双工"。用户态无法看到单条 link 的方向占用，这里的结论是聚合层面的。
