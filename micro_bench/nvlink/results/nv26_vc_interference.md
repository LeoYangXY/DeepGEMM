### nv26_vc_interference — NVLink 流量类型干扰矩阵：全速下互相拖累是纯带宽竞争，30% 负载下三类流量互不影响（无共享队列/VC 瓶颈）

**假设**

如果远端 store / load / atomic 三类流量共用同一套注入队列或同一条虚拟通道（VC），那么即使链路带宽远未打满，它们并发时也会互相拖累（结构性冲突）。反之，如果它们走独立通道或有足够的队列资源，则只有在链路带宽被打满时才会互相分带宽。

区分这两者的唯一办法：**把负载压到远低于链路容量再做并发**。这是本实验的核心控制变量。

**方法**

- 三类流量都从 GPU0 发起、打到 GPU1 的两块**不相交** 128MB buffer（避免地址冲突/伪共享污染结果）：
  - STORE：`st.global.v4.u32`（16B/线程）
  - LOAD：`ld.volatile.global.v4.u32`（volatile 绕开 L1/L2 复用，保证每次真的走链路）
  - ATOMIC：`red.global.add.u32`（fire-and-forget 无返回值，每线程打独立 slot，测的是链路 atomic 吞吐而非 cacheline 争用）
- **并发计时姿势**：两条 CUDA stream 各自 event，先都 launch 出去再统一 `cudaDeviceSynchronize`，各流带宽用自己的 event 算，聚合带宽用 `max(msA,msB)`。
- **关键修正 1 — grid 只开 78 block（每 SM 恰好 1 个）**。最初用 `78*4=312` block 时，两条并发流的 block 数超过 SM 容量，第二条流实际在**排队等 SM 槽位**，测出来的是 SM 调度竞争而非链路竞争（表现为 C2 矩阵每列数字雷同）。降到每 SM 1 block 后两条流才真正同时驻留。
- **关键修正 2 — 节流旋钮要分类型选**。用了两个独立旋钮：
  - 活跃 warp 数（非活跃 warp 直接 return，不发访存）
  - grid 大小（减少参与的 SM 数）

  实测 STORE 是 fire-and-forget，**1 warp/SM 就能灌满链路（367 GB/s ≈ 全速 371）**，warp 旋钮对它完全无效，只能用 grid 旋钮；LOAD 要等返回值、受 outstanding 请求数约束，warp 旋钮对它是干净的线性关系。这个差异本身就是一个微架构结论。
- 节流后逻辑字节数按活跃比例缩放，避免把"少搬了数据"错算成"带宽下降"。

**实测数据**

单类基线（78 block × 256 thr，单次 kernel 17–23 ms）：

| 流量类型 | T_solo (GB/s) | raw/data（线上开销比） |
|---|---|---|
| STORE | 370.5 | 2.039 |
| LOAD | 285.3 | 1.990 |
| ATOMIC | 317.5 | 2.277 |

注入率曲线 A — 活跃 warp 数（grid=78 固定，GB/s）：

|---|---|---|---|---|---|---|
| STORE | 367 | 366 | 367 | 366 | 370 | 371 |
| LOAD | 44 | 88 | 127 | 157 | 218 | 285 |
| ATOMIC | 256 | 292 | 313 | 315 | 316 | 318 |

|---|---|---|---|---|---|
| STORE | 203 | 322 | 371 | 368 | 371 |
| LOAD | 15 | 34 | 72 | 147 | 285 |
| ATOMIC | 197 | 278 | 321 | 317 | 313 |

| A \ B | STORE | LOAD | ATOMIC |
|---|---|---|---|
| **STORE** | (0.50, 0.50) 371 | (0.98, 0.62) 356 | (0.77, 0.24) 361 |

| A \ B | STORE | LOAD | ATOMIC |
|---|---|---|---|
| **STORE** | A=185 B=185 | A=362 B=178 | A=287 B=75 |
| **LOAD** | A=178 B=363 | A=186 B=186 | A=244 B=312 |
| **ATOMIC** | A=75 B=287 | A=306 B=242 | A=162 B=162 |

**【核心】低负载（各 ~30%）并发干扰矩阵**（两条流合计 ~60% 链路容量）：

| A \ B | STORE | LOAD | ATOMIC |
|---|---|---|---|
| **STORE** | (1.00, 1.00) 208 | (1.00, 0.98) 130 | (1.00, 1.00) 203 |
| **LOAD** | (0.98, 1.00) 130 | (0.89, 0.89) 157 | (0.99, 0.99) 133 |
| **ATOMIC** | (1.00, 1.00) 203 | (1.00, 0.99) 133 | (1.00, 1.00) 207 |

节流标定点：STORE grid=4/1warp → 103.8 GB/s (0.28×)；LOAD grid=78/2warp → 88.3 GB/s (0.31×)；ATOMIC grid=4/4warp → 103.6 GB/s (0.33×)。

**结论**

1. **不存在跨流量类型的共享队列/VC 瓶颈。** 依据 C2 矩阵：把两条流各压到 ~30% 带宽后，所有 6 个跨类型组合的比值全部落在 **0.98–1.00**，聚合带宽等于两者之和（如 STORE+ATOMIC 得 203 ≈ 103.8+103.6）。链路只用了 60% 时零干扰 ⇒ 全速下的互相拖累**纯粹是带宽竞争**，不是队列/VC 结构性冲突。这直接否定了"atomic 和 store 共用队列"的假设。

2. **全速下总带宽守恒在 ~370 GB/s**，就是 GPU0→GPU1 方向的注入上限。依据 B2 表：STORE+STORE 得 185+185=370，STORE+LOAD 得 362+178=540（跨方向，见 nv27 全双工），ATOMIC+ATOMIC 得 162+162=324。同类流量并发时**分配完全公平**（对角线全是 0.50/0.50/0.51，方差 <1%），说明注入端是公平轮转仲裁。

3. **STORE 对 ATOMIC 有强烈的不对称压制**：全速 STORE+ATOMIC 时 store 保住 0.77（287 GB/s）而 atomic 只剩 **0.24（75 GB/s）**。但同样组合在 30% 负载下是 (1.00, 1.00)。所以这不是优先级/VC 问题，而是 **atomic 的单请求粒度小（4B）导致它在链路满载时抢不过 16B 的 store 请求**——按请求数仲裁而非按字节仲裁，store 每个请求携带 4× 的净荷。

4. **STORE 是 fire-and-forget，1 warp/SM（78 warp 全卡）即可饱和 367 GB/s**（曲线 A 第一行几乎是平的）；而 LOAD 严格受 outstanding 请求数限制，带宽随活跃 warp 数近似线性（44→88→127→157→218→285，1w 到 8w 增益 6.5×）。这解释了为什么 LOAD solo 只有 285 GB/s 而 STORE 有 370：读被并发度而非链路带宽卡住。

5. **ATOMIC 线上开销最大**：raw/data = **2.277**，高于 STORE 的 2.039 和 LOAD 的 1.990。4B 净荷要配完整包头，协议效率最差。

**不确定性**

- LOAD+LOAD 在低负载下是 (0.89, 0.89) 而非 1.00，是唯一的例外。原因是 LOAD 的 30% 节流点用的是 grid=78（占满所有 SM）+2 warp，两条流的 warp 落在同一批 SM 上，争的是 **SM 的 outstanding load 槽位**（LSU/MIO 队列），不是链路资源。若改用 grid 节流让两条流物理分开 SM 应可消除，本次未做（时间预算）。这不影响"无共享 VC"的主结论，因为其余 5 个组合都是 1.00。
- 节流标定点没能精确命中 30%（实际 0.28/0.31/0.33），因为旋钮是离散的。不影响结论方向。
- 本实验只测了 GPU0→GPU1 单方向单对。是否存在"只在多对多场景下才暴露的 VC 竞争"未覆盖，见 nv28/nv29。
- `red.global.add` 走的是否是与普通 store 相同的物理通道，无法从用户态直接观测，只能由干扰行为反推。
