### nv12_lat_vs_load — 延迟在 95% 利用率前只涨 1.3x，knee 在 bg_grid=8；真正的爆炸(7.5x)发生在 SM 侧超订而非 link 饱和

**假设**
排队论：延迟 `W = W0 / (1 - ρ)`，ρ 为利用率。
- ρ 远小于 1 时延迟近似常数 ⇒ 队列有余量。
- ρ 接近 1 时延迟陡升（knee）⇒ 队列开始堆积。
knee 出现的利用率位置能反映流控的激进程度：knee 越靠近 100%，说明 credit 池越深、
背压越"晚"介入。

**方法**
- 两个 CUDA stream 并发跑在 GPU0 上：
  - `s_bg`：背景负载 kernel，grid 可调（0→312）制造不同强度的远端写。
  - `s_pr`：探针 kernel，1 个线程远端 pointer-chase（256 步依赖链）测单次往返延迟。
- **同步保证探针落在负载稳态中**：背景 kernel 一进入就把 device flag 置 1，
  探针 spin 等 flag 再开始；探针还先跑 64 步预热让自己的 TLB/路径热起来，
  之后才开 `clock64` 计时。背景 kernel 循环 6 遍 buffer，保证比探针活得久。
- 先单独标定每个 grid 的独占带宽（第 1 节），作为该点的"负载强度"刻度；
  再并发测延迟（第 2 节）。两节用同一个背景 kernel，刻度可比。
- 延迟取 best-of-4（最小值 = 最干净的稳态测量，避免被调度抖动污染）。

**实测数据**（`raw_logs/nv12_lat_vs_load.log`）

**结论**

1. **knee point = bg_grid 7→8，延迟从 1.29x 跳到 1.74x。** 依据：bg_grid=7 行
   延迟 1019.1 ns（1.29x），bg_grid=8 行 1381.8 ns（1.74x），**单步跳 35%**。
2. **knee 之前延迟极其平坦，一直平到 94.9% 利用率。** 依据：bg_grid=1..7 的
   `vs idle` 列为 1.01 / 1.20 / 1.27 / 1.22 / 1.29 / 1.30 / **1.29**，
   而同期利用率从 13.7% 一路涨到 **94.9%**。
   **利用率涨 6.9 倍，延迟只涨 29%** ⇒ 在 95% 负载前 NVLink 队列始终有余量，
   这是一个**深缓冲、弱背压**的设计（与 nv11 测出的 credit 池是纯 BDP 的 2.6 倍吻合）。
3. **knee 的成因不是 link 饱和，而是 SM 侧超订。** 这是本实验最重要的发现，依据有二：
   - bg_grid=7 时带宽 351.29 GB/s（94.9%）延迟仅 1.29x；bg_grid=8 时带宽反而**下降**
     到 312.05 GB/s（84.3%）延迟却跳到 1.74x。**带宽更低而延迟更高** ——
     这不可能由 link 拥塞解释。
   - 原因是 nv09/nv10 已证明单 SM 出口仅 50.5 GB/s，7 个 SM × 50.5 = 353.5 GB/s
     刚好够 link 的 370；到第 8 个 SM 时探针所在的 block0 开始与背景 block 争抢
     **同一个 SM 的出口**，排队发生在 SM 内部而非 link 上。
4. **真正的延迟爆炸在 bg_grid=78，达 7.54x（5980.7 ns）。** 依据：bg_grid=48 时
   还是 2.30x（1827.6 ns），bg_grid=78 直接跳到 7.54x，**3.3 倍的阶跃**。
   此时带宽 368.96 与 bg_grid=48 的 366.03 几乎相同 ⇒ 又一次证明延迟爆炸与
   link 利用率无关。78 = 卡上 SM 总数，此时**每个 SM 都被背景负载占据**，
   探针无处可逃，必须与背景线程排队共享出口。
5. **过了 78 之后延迟饱和不再恶化**：78/156/312 分别是 7.54x / 7.93x / 7.66x，
   基本持平。与 nv10 的"无拥塞崩溃"结论一致。

**实用推论**
在 NVLink 通信与计算重叠的场景下，**把通信 kernel 限制在 8 个以内的 SM**
（或用 CUDA stream priority / `cudaLaunchAttributeProgrammaticStreamSerialization`
隔离）就能拿到 95% 的 link 带宽，同时把其他 kernel 的远端访存延迟保持在 1.3x 以内。
一旦通信 kernel 铺满全部 78 个 SM，带宽一点不多（368.96 vs 351.29，+5%），
延迟却恶化 5.8 倍（7.54x vs 1.29x）。**这是一个明确的、可操作的调优结论。**

**不确定性**
- 标定段 bg_grid=8 的带宽 312.05 GB/s 明显低于 bg_grid=7 的 351.29，
  这个"8 个 block 反而更慢"的现象在 nv10 也出现过（grid=8 时 312.90）。
  推测是 block 到 SM 的分配在 8 这个数上不均匀（可能 2 个 block 挤在同一 SM），
  未用 `%smid` 验证。因此 knee 的精确位置（7 还是 8）有 ±1 的不确定性。
- 探针 spin 等 flag 的同步方式保证了"背景已开始"，但不保证"背景已进入稳态"；
  探针预热 64 步（约 50 us）在一定程度上缓解了这个问题，但未精确对齐。
- 延迟取 best-of-4 的最小值，是偏乐观的估计（真实平均延迟会更高）。
  这个选择让 knee 更保守（更难触发），所以"95% 前延迟平坦"的结论是安全的。
- 探针是 load、背景是 store，与 nv11 有同样的读写混用问题。
