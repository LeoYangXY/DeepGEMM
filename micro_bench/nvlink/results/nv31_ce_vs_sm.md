### nv31_ce_vs_sm — Copy Engine 全 size 段完胜 SM 拷贝（396 vs 369 GB/s 峰值），启动开销固定 1.89 µs，CE 确认零 SM 占用（1.009×），但多 stream 并发无任何增益

**假设**

Copy Engine 是独立于 SM 的 DMA 硬件。预期：(1) 大包 CE 效率更高，小包受启动开销拖累，存在一个交叉点；(2) 多个 CE 可并发工作，总带宽随 stream 数提升到引擎数为止；(3) CE 拷贝不占 SM，计算 kernel 性能不受影响。

**方法**

- `cudaDeviceGetAttribute(cudaDevAttrAsyncEngineCount)` 读硬件引擎数作为交叉验证。
- (e) 启动开销：0/4/256/4KB/64KB/1MB 字节的 `cudaMemcpyPeerAsync`，每档 2000 次取平均，小包结果直接反映固定开销。
- (a) size 扫描 4KB→512MB，CE 与 SM kernel 拷贝（`ld128`+`st128`）同条件对比，小 size 重复 2000 次、大 size 20 次，取 best-of-3。
- (b) 多 CE：2/4/8 个 stream 各拷贝一块**不相交** 64MB 区域，墙钟口径算总带宽。
- (c) **CE 零 SM 占用的量化**：跑一个纯 FMA 计算 kernel（完全不碰内存，排除访存干扰），分别在「单独」「+CE 拷贝」「+SM 拷贝」三种情况下测其耗时。**SM 拷贝组是关键对照**——它证明测量方法本身对 SM 竞争是敏感的。
- (d) CE 与 SM 拷贝同时打同一条链路，各自 event 测份额。

**实测数据**

`cudaDevAttrAsyncEngineCount: GPU0=3, GPU1=3`

**结论**

1. **CE 峰值带宽 396.5 GB/s，比 SM 拷贝的 368.6 GB/s 高 7.6%**（依据 (a) 表 512MB 行）。CE 是更接近链路极限的路径：396.5 已达 18×26.562=478 GB/s 理论线速的 82.9%，而 SM 路径只有 77.1%。原因是 CE 的 DMA 引擎能生成更规整的大包序列，不受 SM 侧 warp 调度和 L2 往返的影响。

2. **不存在 CE/SM 交叉点——CE 在全部 10 个 size 档位上都赢。** 这与常见预期相反。依据 (a) 表"胜者"列全为 CE：即使在 4KB 也是 1.88 µs vs 2.51 µs。原因是 SM kernel 的 launch 开销（~2.5 µs）本身就比 `cudaMemcpyPeerAsync` 的 1.89 µs 更大，所以小包段 CE 反而更有优势。**结论：GPU-to-GPU 拷贝在任何尺寸下都应优先用 CE**，除非需要在拷贝途中做计算融合。

3. **`cudaMemcpyPeerAsync` 的固定启动开销 = 1.89 µs。** 依据 (e) 表：4B / 256B / 4KB / 64KB **四个档位的耗时完全相同（1.88–1.89 µs）**，说明 64KB 以内全部被固定开销支配，传输时间可忽略。等效地，**64KB 是 CE 的"免费"传输粒度**。1MB 时升到 4.85 µs，其中约 2.96 µs 是真实传输（1MB/396GB/s≈2.65 µs），与固定开销 1.89 µs 之和吻合。0 字节仅 0.03 µs 是因为驱动直接短路返回，不代表真实提交开销。

4. **多 CE 并发【无任何增益】：1→8 stream 总带宽恒为 389–391 GB/s（1.00x）。** 依据 (b) 表。虽然 `asyncEngineCount=3` 报告有 3 个异步引擎，但**它们无法在同一条 GPU0→GPU1 链路上叠加带宽**——单个 CE 已经能把 390 GB/s 的链路打满，瓶颈是链路/注入而非引擎数。因此 `asyncEngineCount=3` 的实际意义是"可同时服务 3 个**不同方向**的传输"（如 H2D/D2H/P2P 并行），而不是"P2P 带宽可 ×3"。**在单向 P2P 场景下开多 stream 做 memcpyPeer 是无效优化。**

5. **CE 零 SM 占用基本成立，但不是严格的零：计算 kernel 慢了 0.9%（1.009×）。** 依据 (c) 表。关键在于同表的 SM 拷贝对照组慢了 **7.0%（1.070×）**——这证明测量方法确实能捕捉 SM 竞争，因此 CE 的 0.9% 是真实但极小的信号（可能来自 L2 端口竞争或内存控制器仲裁，而非 SM 占用）。**CE 相比 SM 拷贝为计算 kernel 省下了约 6 个百分点的性能**，同时还多跑了 390.3 GB/s 的拷贝。这是 CE 最有价值的特性。

6. **CE + SM 同打一条链路时总带宽 384.1 GB/s，低于 CE 单独的 395.3**（依据 (d) 表），即混用两条路径有约 2.8% 的净损失。份额 CE 55% / SM 45%，大致公平但 CE 略占优。**实践含义：不要为了"榨干带宽"而同时用 CE 和 SM 拷贝，反而不如只用 CE。**

**不确定性**

- (b) 的结论"多 CE 无法叠加"只在**单向 GPU0→GPU1** 场景下验证。多引擎在双向或多 peer 场景下能否叠加未测——考虑到 nv27 已证明双向可达 731 GB/s、nv28 证明出口是 370 GB/s 聚合共享，预期多 CE 在**双向**场景能有增益，但本实验未覆盖。
- (c) 的计算 kernel 只跑 0.21 ms，比 CE 拷贝窗口短很多，测的是"CE 稳定传输期间"的瞬时影响。若计算 kernel 更长（跨越 CE 的启动/收尾阶段），损失可能不同。此外 0.21 ms 的绝对值较小，1.009× 对应的绝对差异接近计时噪声下限，该数值应视为"≤1%"而非精确的 0.9%。
- (a) 中 CE 带宽（396.5）高于 nv27/nv28 测得的 SM 路径 370 GB/s 上限，也高于平台基线记录的 CE 391 GB/s。这说明 **CE 与 SM 走的注入路径能力不同**，nv28 得出的"370 GB/s 是 GPU0 注入上限"应限定为**SM 路径**的上限；CE 路径的上限是 ~396 GB/s。这一点值得后续单独确认。
- 未测 CE 的延迟分布（只有平均值），也未测 CE 在拷贝**非连续/带 stride** 数据时的表现。
