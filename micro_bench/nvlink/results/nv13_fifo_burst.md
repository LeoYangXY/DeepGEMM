### nv13_fifo_burst — INCONCLUSIVE：两种构造都失败，直接测 FIFO 深度存在方法论上的死结（容量数值请引用 nv11 的 770 KB）

**假设**
经典 FIFO 深度探测法：发一个长度 B 的远端 store burst → 空闲 S ns → 再发一个 burst，
逐条记录第二个 burst 中每条访存的间隔。
只要下游缓冲还有空位，指令就能立刻退休（间隔小）；缓冲填满后必须等 credit 回来
（间隔跳到后端服务间隔）。**前 N 条便宜、第 N+1 条变贵的那个 N 就是缓冲深度。**
S 越大，第一个 burst 留下的积压排空越干净，N 应当越大 —— 由此可反推排空速率。

**方法与两次迭代**
所有版本都遵守：时间戳先存 shared memory、kernel 末尾一次性写回 global
（循环内绝不碰 global，否则污染测量）；`__nanosleep` 制造空闲；
地址按 nthr 步进保证每条访存都是全新的 128B 行。

**v1（单 warp store）—— 失败**
`grid=1, block=32`，单 warp 发 burst。
结果（`raw_logs/nv13_fifo_burst.v1.log`）：**所有 (B,S) 组合、远端和本地，
间隔全都是恒定 64 cyc，knee 一律为 none。**

失败原因（已定位）：单 warp 的发射速率 = 512B / (64 cyc @1.98GHz) = **15.8 GB/s**，
而 NVLink 后端排空速率是 **370 GB/s**，慢了 **23 倍**。
**探测器比被测对象弱 23 倍，缓冲永远填不满**，自然测不到 knee。

**v2（多 SM store，grid=12×1024 线程）—— 失败，且被自身数据证伪**
提高聚合发射速率到理论上超过后端。
结果（`raw_logs/nv13_fifo_burst.log` A~E 段）：间隔序列形态**与预期相反** ——
开头高（~700 cyc）、结尾低（160 cyc），knee 基本为 none。

判决性证伪在 E 段（扫 GRID）：

| grid | step KB | 稳态 cyc | 算出的"发射速率" |
|---|---|---|---|
| 1 | 16.0 | 220.9 | **146.8 GB/s** |
| 4 | 64.0 | 220.3 | **589.0 GB/s** |
| 12 | 192.0 | 251.6 | **1547.1 GB/s** |
| 32 | 512.0 | 261.3 | **3972.6 GB/s** |

nv09 已证明**单 SM 远端写上限是 50.4 GB/s**、全卡上限 370 GB/s。
grid=1 算出 146.8 GB/s、grid=32 算出 3972.6 GB/s，**物理上不可能**。
⇒ 时间戳测的根本不是访存完成间隔。

根因：`st128` 是 **fire-and-forget**，没有目的寄存器，
`clock64` 与 store 的完成之间**不存在任何数据依赖**，编译器和硬件都可以让
记录 lane 跑在真实内存流量前面。测出的只是**指令发射槽间隔**。
B 段的"稳态服务速率 1607 GB/s"是同一个错误的另一种表现。
C 段本地 HBM 对照呈现完全相同的形态，进一步确认这是测量伪影而非 NVLink 特性。

**v3（多 SM load + 强制依赖）—— 自洽但无法回答原问题**
换成 `ld128_v`，用 inline asm 把返回值 `acc` 喂进 `clock64` 之前的一条假指令
（`and.b32 t, %1, 0`），强制 `clk()` 排在 load 返回之后，建立真依赖。

结果（`raw_logs/nv13_fifo_burst.log` F/F2 段）：

| grid | step KB | 稳态 cyc | knee N |
|---|---|---|---|
| 1 | 16.0 | 1694.6 | **none** |
| 2 | 32.0 | 1700.8 | **none** |
| 4 | 64.0 | 1695.5 | **none** |
| 8 | 128.0 | 1890.2 | **none** |
| 12 | 192.0 | 2092.2 | **none** |

F2 逐条明细（grid=1）：`1794 1726 1715 1791 1674 1694 1792 ...` —— **完全平坦，无任何拐点**。
S=0 与 S=10000ns 的序列几乎逐条相同（稳态 1693.3 vs 1695.0 cyc）。

这次数据是**自洽**的：稳态 1693.3 cyc = 855.2 ns，与 nv08 测的远端 load 延迟
838.6 ns、nv11 的空载 798.9 ns 属于同一量级，说明测量口径正确。
但正因为强制了依赖，**每次迭代必须等一个完整往返**，并发度被压成 1 ——
测到的是**延迟**，不是缓冲深度。

**结论：INCONCLUSIVE**

本实验无法直接给出 FIFO 深度 N 和排空时间，原因是一个**方法论死结**：

> 让 `clock64` 可信所需的**数据依赖**，恰恰摧毁了填满缓冲所需的**并发度**。
> - store 有并发但不可观测（无依赖 ⇒ 时间戳无意义，v2 被自身数据证伪）
> - load 可观测但无并发（有依赖 ⇒ 每次等一个往返，v3 全程平坦）

在 GPU 上用 `clock64` 逐条采样来探测 fire-and-forget 写缓冲的深度，
在本平台上不可行。要真正测出来需要下列手段之一（本次时间预算内未做）：
- 硬件性能计数器采样在途请求数（需要 CUPTI / `nvlink__*` 指标，非 nvidia-smi 可得）
- 用 `red.global.add` 等**有完成确认**的远端原子操作代替 store，
  这样既保留并发（多线程各自发）又有可观测的完成事件
- 在两端各放一个 kernel，用远端 flag 的到达时序间接推断（需要跨 GPU 时钟对齐）

**缓冲容量的数值请引用 nv11：770 KB（≈6157 个 128B 请求，每 link 342 个）。**
nv11 用 Little's Law 绕开了这个死结 —— 它不需要观测单个请求的完成时刻，
只需要聚合吞吐和平均延迟，两者都能可靠测量。

**有价值的副产品（这些数字本身可信）**
1. **单 warp 的远端 store 发射速率 = 64 cyc / 512B 事务 = 15.8 GB/s**
   （v1 log，所有 B/S 组合恒定）。这解释了 nv09 中"1 warp 只有 25.8 GB/s、
   需要 2 warp 才到 50.4"的现象。
2. **远端 store 的 burst 行为对空闲时间 S 完全不敏感**：v2 A 段中 B=256 时
   S=0/100/1000/10000ns 的总 cycle 分别是 163903/163840/163741/163764，
   **差异 <0.1%**。在 8~256 的 burst 长度范围内，没有观测到任何需要"排空"的积压。
   结合 nv11 的 770 KB 容量：B=256 时单 warp 只发了 256×512B = 128 KB，
   **确实还没填满 770 KB 的池子**，所以看不到排空效应是符合预期的。
3. v3 的稳态 1693.3 cyc = 855.2 ns 是对 nv08 远端 load 延迟（838.6 ns）的
   **独立复现**（用完全不同的 kernel 结构），误差 2.0%。

**不确定性**
- 上述"方法论死结"的论断基于本次三种构造；不排除存在更巧妙的构造能同时保住
  并发与可观测性（例如按 warp 分工：一部分 warp 只发压力、另一部分只做带依赖的
  探测，且两者在时间上严格对齐）。时间预算内未尝试。
- v2 的 D 段（细扫 S）出现过几个非 -1 的 knee 值（S=5000 时 knee=14、
  S=20000 时 knee=100），但这些值在不同 S 之间毫无单调性（20000→100 但 50000→20），
  且来自已被证伪的 store 测量，**不应采信**。
