### nv21_atomic_tput — 远端原子吞吐上限 6.6 Gops/s（本地 75 Gops/s，11.4× 差距），满竞争时每次 L2 原子 86.8 ns 而非 861 ns 的往返

**假设**

远端原子的吞吐上限由什么决定？两种可能：(a) 每次原子都要一个完整跨卡往返，那满竞争吞吐应该 ≈ 1/861ns = 1.16 Mops/s；(b) 请求送到远端 L2 就地流水化执行，那吞吐会远高于 1.16 Mops/s，因为多个请求可以在链路上重叠。同时想知道无竞争时远端原子能不能打满 NVLink 的 370 GB/s。

**方法**

grid=624 (78 SM × 8), block=256 → 159744 线程，每线程 64 次原子，共 10.2 M ops/kernel。用 `cudaEvent` 计时整个 kernel，Mops/s = 总原子数 / 时间。

目标地址数 NSLOT 从 1 扫到 1M。两种内存布局都测：slot 间隔 4B（多个 slot 挤在同一条 line 内）和 128B（每 slot 独占一条 line），因为 GPU L2 原子按 sector 仲裁，布局会改变结论。

**踩过的坑（重要，影响结论解读）**：第一版把 slot 索引写成 `tid % nslot`，导致一个 warp 的 32 个 lane 全部映射到同一个 slot。SM 会做 **intra-warp 原子聚合**——32 次原子在 warp 内先合并成 1 次再发出去。结果是本地和远端吞吐完全相同（都是 21.3 Mops/s）且随 NSLOT 完美 ×2 缩放，测的其实是指令发射速率而不是原子单元速率。修正为让 lane 走索引最低位：

```c
unsigned s = (lane + warp * 32u) % nslot;
```

这样 NSLOT ≥ 32 时 warp 内 32 个 lane 落到 32 个不同 slot，聚合被打散。NSLOT < 32 时物理上无法避免聚合，聚合倍数 = 32/NSLOT，已在表中单列标出，换算时必须除掉。

关键换算（log 47–60 行）

```
满竞争 NSLOT=1 (含 32:1 intra-warp 聚合, L2 侧真实请求 = 名义/32):
  远端 atom  368.8 Mops/s(名义) -> L2侧 11.5 Mops/s -> 每次L2原子 86.76 ns
  本地 atom 1366.4 Mops/s(名义) -> L2侧 42.7 Mops/s -> 每次L2原子 23.42 ns
无竞争 NSLOT=1M:
  远端 atom 6599.7 Mops/s = 26.4 GB/s ; 本地 atom 75285.8 Mops/s = 301.1 GB/s
```

**结论**

1. **满竞争时每次 L2 原子只要 86.8 ns，远小于 861 ns 的单次往返 —— 原子请求在链路上是流水化的，不是一次一个往返。** 依据「关键换算」段：NSLOT=1 远端名义 368.8 Mops/s，除掉 32:1 warp 聚合后 L2 侧 11.5 Mops/s，即 86.76 ns/op。**861 / 86.8 = 9.9×**，说明同一时刻链路上至少有 ~10 个原子请求在飞。这排除了「每次原子都要等一个完整往返」的模型。但注意：这还不能区分流水发生在本地还是远端 —— 那是 nv22 用线上字节计数器解决的。

2. **远端原子吞吐硬上限 = 6.6 Gops/s，只有本地的 1/11.4。** 依据布局 A NSLOT=1M 行：远端 6601.4 vs 本地 75374.6 Mops/s。远端从 NSLOT=128 (5796.9) 开始就基本饱和，1024 反而略降到 5709.4，到 65536 才回到 6502.5 —— **竞争度超过 128 之后再降低竞争已经没有收益，瓶颈从「同地址串行化」切换成了「链路/远端 L2 原子单元的总吞吐」**。本地则一直涨到 65536 才饱和（75345），说明本地的瓶颈点在更后面。

3. **远端原子远远打不满 NVLink：6.6 Gops × 4B = 26.4 GB/s，只有 370 GB/s 基线的 7.1%。** 依据「关键换算」无竞争段。原因是每个 4B 原子要占用一个完整的请求包（nv22 实测 16 B/op 线上净荷），协议开销比 4:1 还差，加上原子无法像顺序写那样合并成 128B 事务。**结论对上层的意义：跨卡 all-reduce 绝不能用逐元素远端原子实现，会浪费 93% 的链路带宽。**

4. **把多个 slot 挤进同一条 line 反而快 7.4×。** 对比两种布局 NSLOT=1M：4B 间隔 48662.9 vs 128B 间隔 6601.4 Mops/s。原因是 4B 布局下一个 warp 的 32 个 lane 落在连续 128B 内，**可以合并成一个 line 事务发过去，在远端 L2 一次性对 32 个不同 dword 做原子**。这是个很实用的优化点：远端原子的目标地址应该按 warp 连续排布，能拿到 7× 吞吐。48662.9 Mops × 4B = 194.7 GB/s，达到 370 GB/s 基线的 53%，比 128B 布局的 7% 好得多。

5. **`red`（无返回）和 `atom`（有返回）在高竞争下吞吐完全相同。** `.sys` 对照表旁边的数据：NSLOT=32 时远端 atom 2947.7 / red 2948.0；NSLOT=1M 时 6601.4 / 6592.0。只有在**本地**无竞争时 red 才明显更快（本地 1M：atom 75374.6 vs red 94133.2，快 25%）。说明远端场景下瓶颈是请求通道本身，省掉返回值救不了；nv20 里 red 的优势是**延迟**（线程不用等），不是吞吐。

6. **`.sys` scope 对吞吐零影响。** `.sys` 对照表 9 行数据两列几乎逐位相同（如 NSLOT=1M：6601.9 vs 6601.4，差 0.008%）。与 nv20 的延迟结论一致。

**不确定性**

- NSLOT ≤ 8 的行受 intra-warp 聚合污染，表中已标注聚合倍数，但聚合是否严格按 32/NSLOT 生效没有独立验证（NSLOT=2 在 128B 布局下本地吞吐 1179.4 反而低于 NSLOT=1 的 1366.4，不符合简单模型，可能是两条 line 分属不同 L2 slice 带来的额外仲裁）。真正干净的满竞争对照应看 NSLOT=32 行。
- 布局 A 中 NSLOT=1024 (5709.4) 略低于 NSLOT=128 (5796.9)，这个非单调下降幅度 1.5%，接近测量抖动，未深究。
- 26.4 GB/s 是按 4B 有效载荷算的；若按 nv22 实测的 16 B/op 线上净荷算，实际占用链路 6.6 G × 16 B = 105.6 GB/s，即链路利用率约 28% 而非 7%。两个数字回答的是不同问题（有效 vs 占用）。
