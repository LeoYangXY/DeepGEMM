### nv32_linkstripe — 18 条 link 的流量分配与地址条带粒度 = 256 B

**假设**：GPU0 有 18 条物理 link 接到 4 颗 NVSwitch。一次 GPU0→GPU1 的写请求，硬件按某种规则把请求摊到这 18 条上。这个规则（是否均衡、按什么粒度切、是不是按目标静态划分）官方一个字都没写。

**方法**：NVML 能读**每条 link 单独的** Data Tx/Rx 字节计数器。于是：snapshot 18 条 → 跑一个**地址范围受控**的负载 → 再 snapshot → 相减，就能直接看见每条 link 分到多少字节。
关键设计是 B 段：把写限制在一个大小为 W 的地址窗口内反复写（总 payload 固定 2 GB，只改 W）。若 W 小时只有 k 条 link 有流量，W 增大后 k 涨到 18，则「让 18 条全用上所需的最小 W」除以 18 就逼近条带粒度。这是唯一能从外部观测到条带粒度的手段。

**实测数据**

A) 大范围顺序写（payload 4295 MB）：

| 方向 | 总量 | 活跃 link | 每 link 最大 | 每 link 最小 | 变异系数 CV |
|---|---|---|---|---|---|
| GPU0 Tx | 4295.0 MB | 18/18 | 239.08 MB | 238.34 MB | **0.001** |
| GPU0 Rx | 0.0 MB | 0/18 | 0 | 0 | — |

B) 地址窗口扫描（总 payload 固定 ~2 GB）：

| 窗口 W | 活跃 link 数 | CV | 有流量的 link 编号 |
|---|---|---|---|
| 256 B | **1** | 4.123 | 0 |
| 512 B | **2** | 2.828 | 0,1 |
| 1 KB | 4 | 1.871 | 0,1,8,9 |
| 2 KB | 6 | 1.541 | 0,1,8,9,16,17 |
| 4 KB | 10 | 0.984 | 0,1,2,3,8,9,12,13,16,17 |
| 8 KB | **18** | 0.354 | 全部 |
| 16 KB | 18 | 0.269 | 全部 |
| 64 KB | 18 | 0.104 | 全部 |
| 128 KB | 18 | 0.053 | 全部 |
| 4 MB | 18 | **0.016** | 全部 |

C) 同样流量发给不同 peer（每次 payload 2147.5 MB）：

| 负载 | 总 Tx | 活跃 link | CV |
|---|---|---|---|
| GPU0→GPU1 | 2147.5 MB | 18/18 | 0.001 |
| GPU0→GPU2 | 2147.5 MB | 18/18 | 0.001 |
| GPU0→GPU3 | 2147.5 MB | 18/18 | 0.001 |
| GPU0→{1,2,3} 同时 | 6442.5 MB | 18/18 | 0.001 |

三种单目标负载的 per-link 分布**逐条完全一致**（119.5 / 119.2 / 119.2 / …）。

**结论**

1. **地址→link 的条带粒度 = 256 B**。依据是 B 段前两行：W=256 B 时只有 1 条 link 有流量，W=512 B 时恰好 2 条。若粒度是 128 B，W=256 就该点亮 2 条；若是 512 B，W=512 仍只该点亮 1 条。只有 256 B 同时满足这两行。

2. **映射是 hash，不是顺序轮转**。W=1 KB（4 个 256B 块）点亮的是 link {0,1,8,9} 而不是 {0,1,2,3}；W=2 KB 点亮 {0,1,8,9,16,17}。顺序轮转不可能跳着走。且 link 恒成对出现（每对两条数值完全相同），说明最低位那一级是 2 路对分。

3. **要用满 18 条 link，地址跨度至少 8 KB**（32 个 256B 块）。这对小消息是硬约束：一个 4 KB 的 P2P 传输最多只能用到 10/18 = 56% 的链路，一个 512 B 的只能用 2/18 = 11%。这直接解释了为什么小包 P2P 带宽上不去——不是延迟问题，是**物理链路根本没被点亮**。

4. **负载均衡质量随跨度提高**：CV 从 8 KB 的 0.354 一路降到 4 MB 的 0.016。要拿到接近理想的均衡，地址跨度需要 ≥128 KB（CV 0.053，即 512 个条带块）。

5. **18 条 link 完全聚合共享，不按目标静态划分**。依据是 C 段：发给 GPU1/2/3 的 per-link 分布逐条一致（都是 119.5/119.2/…），且同时发给 3 个目标时每条 link 的量正好变成 3 倍（358.6 ≈ 3×119.5）。如果 link 按目标划分，三种负载应该点亮不同的 link 子集。

6. **NVLink 写是完全 posted 的**：A 段 GPU0 Rx = 0.0 MB。发出 4295 MB 的写，Data 方向没有任何返回流量。写不等确认（确认走的是 link 层 flow-control flit，不计入 Data 计数器）。

7. Data 计数器精确等于 payload：发 4295.0 MB 数了 4295.0 MB，可以放心当净荷标尺用。

**不确定性**
- 「256 B 条带」是从 link 点亮数推的，没有直接看到硬件配置寄存器。另一种等价解释是「条带粒度 128 B 但相邻两个 128B 块被映射到同一条 link」，从外部无法区分这两者。
- hash 函数的具体形式没解出来，只知道不是顺序轮转、且低位是 2 路对分。要解出完整 hash 需要逐个 256B 块单独打流量，测试次数是 18×N 量级，超出本次时间预算。
- CV 里含背景噪声（其他进程/驱动心跳），但量级远小于信号（每次测量 payload ≥ 2 GB）。
