### nv22_atomic_where — 判决：远端原子**在远端 L2 就地执行**，不是拉回本地做。线上流量严格 ∝ N，且 `red` 的 Rx 精确为 0

**假设**

两个互斥假说：

- **H_local**（拉回来做）：远端 `atomicAdd` 把 cache line 拉到本地 L2，在本地做 RMW，再写回。特征：同一条 line 被本地独占后，后续 N 次原子都在本地完成，**线上流量与 N 无关**（只有最初的 line fetch + 最后的 writeback）。
- **H_remote**（送过去做）：请求包发到远端 L2，在远端原子单元就地 RMW，结果/ack 回来。特征：**线上 Tx/Rx 都严格正比于 N**，且 `red`（不需要返回旧值）的 Rx 应显著小于 `atom`。

**方法**

三条独立证据，其中 B 是判决性的。

- **(A) 满竞争吞吐 vs 往返延迟**：所有线程打同一个远端地址，看每 op 的串行化间隔是否接近 861 ns（nv20 实测单次往返）。
- **(B) 线上字节计数 —— 判决实验**：用 `nvl_read_counters` 抓 NVLink 硬件 Data 字节计数器。跑 N 次单地址远端原子，把 iter 从 500 扫到 4000（总 ops 变化 8 倍），看流量是否同比例变化。H_local 预测流量恒定，H_remote 预测线性 —— 二选一，无歧义。
- **(C) `atom` vs `red` 的 Rx 对比**：若在远端执行，`atom` 要把旧值送回，Rx 应有 N 个响应包；`red` 不需要，Rx 应接近 0。

计数器有 ~100 ms 采样粒度且是全卡累积值，所以每次测量前后各 `usleep(400000)` 隔离，并且同时抓 GPU0（发起方）和 GPU1（目标方）交叉验证。总 ops 取到 3.2 亿次，让信号远超背景噪声。grid=312, block=256 → 79872 线程。

**结论**

1. **判决：H_remote 成立，远端原子在远端 L2 就地执行。H_local 被完全排除。** 依据证据 B 的 atom 四行：ops 从 39.9 M → 79.9 M → 159.7 M → 319.5 M（8 倍），G0 dTx 同步从 20.0 → 39.9 → 79.9 → 159.7 MB（8 倍），**B/op 恒定为 0.50，四行完全一致**。如果原子是拉回本地 L2 做的，同一条 line 被独占后这 3.2 亿次原子应该几乎不产生线上流量，dTx 会是个与 N 无关的小常数。实测是严格线性 —— **每一次原子操作都真实地过了一趟线**。

2. **`red` 的返回通道流量精确为 0，证实响应包就是「送回旧值」。** 依据证据 B 的 red 四行：G0 dRx 全部是 **0.0 MB / 0.00 B/op**，而 Tx 与 atom 完全相同（0.50 B/op）。对照 atom 的 Rx = 0.50 B/op。**这直接证明了 atom 的 Rx 流量 100% 是返回旧值的响应包**，与 nv20 测到的「atom 比 red 慢 1659 cyc」互为印证：那 1659 cyc 就是等这个响应包回来的时间。`red` 是真正的 fire-and-forget，连线上都不产生回程流量。

3. **单次远端原子的线上净荷 = 16 B（请求）+ 16 B（响应）。** 依据证据 C 「无竞争(独占line)」两行：B/op Tx = **16.00**，B/op Rx = **16.00**，精确到小数点后两位。这是每 lane 打自己独占 128B line、无任何聚合时的真实每操作成本。**一个 4 B 的 atomicAdd 在线上要付 16 B 请求 + 16 B 响应 = 32 B，协议放大 8×**，这解释了 nv21 里远端原子只能拿到 26.4 GB/s 有效带宽（占用链路其实是 105.6 GB/s）。用 `red` 可以砍掉一半（省掉 16 B 响应）。

4. **单地址场景的 0.50 B/op 是 32:1 intra-warp 聚合的直接证据。** 16.00 / 0.50 = 32.0，正好等于 warp 宽度。所有 lane 打同一地址时 SM 先在 warp 内合并成 1 个请求，所以摊到每个名义 op 上只有 16/32 = 0.5 B。这与 nv21 中的聚合修正系数完全吻合，两个独立实验相互验证。

5. **计数器可信，背景噪声为零。** 依据证据 C 最后一行：本地 atom 跑了 159.7 M 次，G0 dTx / dRx 都是 **0.0 MB**。同时 GPU0 的 Tx 与 GPU1 的 Rx 在所有行都逐位相等（如 79.9 = 79.9），双向交叉验证一致。所以上面的线性关系不是采样伪影。

6. **证据 A 单独无法判决，但排除了「每次一个完整往返」的模型。** 远端满竞争 0.0847 ns/op，比 861 ns 快 10159×。这说明请求在链路上高度流水化。但流水化在本地做（H_local）和在远端做（H_remote）都能解释，所以 A 只是必要不充分 —— 真正定案的是 B。这里把 A 单列出来是为了说明「快 ≠ 在本地做」这个常见误判。

7. **附带发现：远端 `st32` 单地址只用了 0.19 ms（比 atom 的 13.74 ms 快 72×），且线上流量仅 0.1 MB。** 说明连续写同一地址被 SM/L2 彻底合并掉了（后写覆盖前写，只有最后一个值需要过线）。**原子不享受这个优化 —— 因为每次 RMW 的结果都可能被观察到，语义上不允许合并。** 这是原子相对普通写的根本成本来源。

**不确定性**

- 16 B/op 是 NVLink Data（协议净荷）计数器的读数，不含 link 层 flit 头和 CRC。nv06 测得 raw/data ≈ 2.0，所以实际线上原始字节可能接近 32 B/op 单向。本文给出的是净荷口径。
- 证据 B 的 iter 只扫了 8 倍范围（500→4000）。虽然线性度极好（B/op 四行完全相同），但没有扫到更大范围去排除「流量随 N 亚线性增长」的极端情形。考虑到 B/op 精确恒定，这个风险很低。
- 「远端就地执行」的具体单元位置（远端 L2 的 ROP 原子单元 vs NVSwitch 内部）本实验无法区分。计数器只能证明请求过了 GPU0 的线并到达了 GPU1，中间是否在 switch 里做了什么看不到。不过 GPU1 的 dRx 与 GPU0 的 dTx 严格相等，说明请求确实抵达了 GPU1 而不是在 switch 被截胡，所以「在 GPU1 的 L2 执行」是最合理的解释。
