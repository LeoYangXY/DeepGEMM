## 时间单位换算

SM 时钟 1980 MHz，所以：

```
1 cycle = 0.505 ns = 5.05e-4 us
1 us    = 1980 cycles  (记成 ~2000 好算)
```

| 事件 | cycles | 时间 |
|---|---|---|
| FFMA 依赖延迟 | 4.45 | 2.2 ns |
| `__syncwarp()` | 1-9 | 0.5-4.5 ns |
| shared 访问 | 29 | 15 ns |
| `__syncthreads()` (256 thr) | 29 | 15 ns |
| DSMEM (邻居 block) | ~190 | 96 ns |
| L2 命中 | 295 | 149 ns |
| HBM | 335 | 169 ns |
| `__threadfence()` | 474 | 239 ns |
| NVLink 远端读 | 1583 | **0.8 us** |
| kernel launch 地板 | ~3560 | **1.8 us** |
| launch + sync | ~13760 | **6.9 us** |

> **1 us ≈ 2000 cycles ≈ 6 次 HBM 往返 ≈ 450 条 FFMA 依赖链。** 单次访存只有 0.17 us，所以性能问题从来不是"某一次访存慢"，而是"几万次访存 × 模式很烂"累积出来的。
>
> 注意该换算只对 **SM 时钟域**成立（`clock64()` 读的就是它）。显存控制器、NVLink、copy engine 各有独立时钟域，那些地方的 GB/s 不要用 SM 时钟反推 cycle。

# A. 全局访存与缓存层级

## A1 `m_gmem` — 访存模式决定一切

| 模式 | 带宽 |
|---|---|
| 连续 scalar | 2977 GB/s |
| stride=32 (每 warp 摸 32 条 line) | 238 GB/s |
| 随机置换 | 163 GB/s |
| 连续 `float4` 向量化 | **3813 GB/s** |

> 同样的数据量，只改访问模式，带宽差 **23 倍**。向量化 `float4` 比 scalar 再快 28%——因为一条 LDG.128 替掉四条 LDG.32，省的是**发射槽**而不是带宽。

## A2 `m_l2sweep` — L2 容量悬崖

固定总访问量，扫 working set：

| WS | GB/s | 所在层级 |
|---|---|---|
| 16 KB – 512 KB | ~7620 | L1/L2 命中 |
| 1 MB – 16 MB | 7112 → 6724 | L2 |
| 32 MB | 6132 | L2 接近满 |
| **64 MB** | **3568** | **掉出 60MB L2 → HBM** |
| 128 MB – 512 MB | 3542 → 3338 | HBM |

> L2 带宽是 HBM 的 **2.0 倍**。悬崖精确出现在 60 MB L2 容量处。这就是为什么 GEMM 要做 L2-aware 的 tile 调度（swizzle block 顺序让同时在跑的 block 复用同一片 L2）。

## A3 `m_latency` — 延迟数字

| 层级 | cycles | ns |
|---|---|---|
| L2 命中 | 295 | 149 |
| HBM | 335 | 169 |
| Shared (本地) | 29 | 15 |
| DSMEM (邻居 block) | 181–198 | 91–100 |
| 远端 GPU (NVLink) | 1583 | 799 |

依赖链上的指令延迟：FFMA 11.7 ns / FADD 12.6 / IMAD 15.1 / DFMA 33.3。

> **HBM 只比 L2 慢 40 cycles**。Hopper 的 L2 优势主要在**带宽**不在延迟。要掩盖 335 cycle，单 warp 的 ILP 根本不够，必须靠 warp 数量。

## A4 `m_tlb` — TLB 几乎摸不到

pointer-chase，stride 从 4 KB 扫到 128 MB：

| stride | cyc/hop |
|---|---|
| 4 KB – 4 MB | 284 |
| 8 MB | 287 |
| 16 – 32 MB | 295 |
| 64 MB | 303 |
| 128 MB | 311 |

> 跨 128 MB 的随机跳转只比密集访问贵 **9.5%**。Hopper 用大页 + 巨大 TLB，CPU 上那种灾难性的 TLB miss 在 GPU 上基本不存在。**别为 TLB 做优化，去优化 coalescing。**

# B. 发射、占用率与指令代价

## B1 `m_occ` — 延迟隐藏需要多少 warp

访存受限 kernel，用 shared 用量卡住每 SM 的 block 数：

| warps/SM | GB/s | 占峰值 |
|---|---|---|
| 4 | 405 | 12% |
| 8 | 800 | 23% |
| 16 | 1529 | 44% |
| 24 | 2164 | 63% |
| 32 | 2635 | 77% |
| 48 | 3164 | 92% |
| 64 | 3443 | 100% |

> 带宽和 warp 数**几乎线性**直到 48 warps。要吃满 HBM 至少需要 **48 warps/SM (75% occupancy)**。这条曲线是"提高 occupancy 到底值不值"的直接答案：对访存 kernel，值。

## B2 `m_ilp` — ILP 能替代 occupancy

单 warp 内独立 FFMA 依赖链数量扫描：

| 链数 (ILP) | cyc/FFMA | 单 warp FFMA/cyc |
|---|---|---|
| 1 | 4.45 | 0.22 |
| 2 | 2.57 | 0.39 |
| 4 | **1.32** | 0.76 |
| 8 | 1.56 | 0.64 |
| 16 | 1.28 | 0.78 |

warp 数扫描（每 SM IPC，上限 4 = 4 个 SMSP）：

| 配置 | IPC/SM |
|---|---|
| ILP=1, 1 warp | 0.22 |
| ILP=1, 32 warps | 3.34 |
| **ILP=4, 4 warps** | **3.04** |
| ILP=4, 16 warps | 3.62 |

> **FFMA 依赖延迟 ≈ 4.45 cycles**，正好等于"要 4 条独立链才能填满流水线"。**ILP=4 配 4 个 warp，就能达到 32 个 warp 的 91% 性能**——这就是为什么高性能 GEMM 用大 tile + 大量寄存器累加器（低 occupancy 但高 ILP）反而更快。

## B3 `m_ops` — 指令代价换算表（以 FFMA 为 1.0）

浮点：

| 指令 | cyc/op (单 warp) | IPC/SM | 相对 FFMA |
|---|---|---|---|
| FFMA / FADD / FMUL | 1.2–1.3 | 3.6–4.2 | **1.0** |
| `__frcp_rn` | 76.7 | 0.295 | 12.3x |
| `__fdividef` | 15.3 | 0.488 | 7.4x |
| `/` 精确除法 | 57.8 | 0.233 | **15.6x** |
| `rsqrtf` | 15.1 | 0.494 | 7.4x |
| `sqrtf` | 56.7 | 0.320 | 11.3x |
| `__sinf` (MUFU) | 12.8 | 0.497 | 7.3x |
| `sinf` (精确) | 76.5 | 0.146 | **24.9x** |
| `__expf` | 16.1 | 0.477 | 7.6x |
| `expf` | 18.3 | 0.377 | 9.6x |
| `__logf` | 15.5 | 0.492 | 7.4x |
| `tanhf` | 101.0 | 0.205 | 17.7x |
| `powf` | 96.4 | 0.227 | 16.0x |
| **FP64 FMA** | 64.0 | 0.062 | **58.2x** |
| `half2` HFMA2 | — | 1.84 | 2.0x/指令 (1.0x/FLOP) |

整数：

| 指令 | 相对 FFMA |
|---|---|
| IADD | 0.29x (最便宜) |
| IMAD / IMUL 32b | 1.8x |
| 64-bit ADD | 1.9x |
| 64-bit MUL | 7.7x |
| `funnelshift` | 2.1x |
| `max` | 3.9x |
| `popc`/`clz`/`brev` | 7.3x (走 MUFU) |
| 整数 `%` | 14.3x |
| 整数 `/` | **20.1x** |

> 三条黄金规则：**(1)** 用 `-use_fast_math` 或手写 `__xxxf`，精确 `sinf` 比快速版贵 3.4 倍；**(2)** H20 上 FP64 是 FP32 的 1/58，任何 `double` 都是灾难；**(3)** 整数除法/取模比 FFMA 贵 14–20 倍，换成位运算或预计算倒数。

## B4 `m_div` — 分支代价

| 模式 | 耗时 | 相对 |
|---|---|---|
| 无分支 | 123.9 ms | 1.00x |
| **一致分支**（整 warp 同走向） | 169.4 ms | **1.37x** |
| 发散分支（奇偶线程分叉） | 174.4 ms | 1.41x |

> 反直觉结论：**分支指令本身的开销 (1.37x) 远大于发散的额外开销 (1.03x)**。也就是说，让 warp "不发散"只省了 3%，而"干脆别写分支"能省 27%。优先用 `fmaf`/`min`/`max`/select 消灭分支，而不是费劲去对齐 warp 边界。

## B5 `m_issue` — warp scheduler (SMSP) 争用

同 block 内一个 warp 狂做 ld/st、另一个做计算：

- 两 warp 落在**同一个 SMSP**：计算 warp 损失 **≤ 8.8%**
- 两 warp 落在**不同 SMSP**：损失 **0%**
- 单 warp IPC ≈ 0.5，同 SMSP 双 warp IPC ≈ 1.0（发射槽被填满）

> 每 SM 有 4 个 SMSP，warp i 固定去 `i % 4` 号 SMSP。**warp specialization 时把 producer 和 consumer 的 warp id 错开 4 的余数，就能完全避开发射槽争用。** ncu 的 `not_selected` stall 在同 SMSP 时会非常高，但那是两个 warp 合并统计的结果，会高估实际损失。

# C. Shared Memory / cp.async / TMA / 集群

## C1 `m_lds` — Shared 带宽与位宽

| 位宽 | cyc/inst (8 warp) | B/clk/SM |
|---|---|---|
| LDS.32 | 1.00 | 128 |
| LDS.64 | 2.00 | 128 |
| LDS.128 | 4.00 | 128 |
| LDS.128 (32 warp) | 1.00 | **512** |

单 warp 延迟：LDS.32 = 4.16 cyc，LDS.128 = 8.19 cyc。

> **每个 SMSP 的 shared 带宽固定 128 B/clk**，与位宽无关。用 `float4` 不是为了更多带宽，而是**用 1/4 的指令数拿到同样的数据**，把发射槽让给计算。四个 SMSP 齐开时全 SM 可达 512 B/clk。

## C2 `m_lds` bank conflict — 完美线性惩罚

| 冲突度 | cyc/inst | 相对无冲突 |
|---|---|---|
| broadcast (全 warp 同地址) | 1.00 | 1x (免费) |
| 无冲突 | 1.00 | 1x |
| 2-way | 2.00 | 2x |
| 4-way | 4.00 | 4x |
| 8-way | 7.99 | 8x |
| 16-way | 16.00 | 16x |
| 32-way | 32.00 | **32x** |

> 冲突惩罚**严格线性**，没有任何硬件缓解。广播完全免费。32-way 冲突让 shared 慢到比 L2 还差。

## C3 `m_swizzle` — padding vs XOR swizzle

对 `half[64][64]` tile 做列方向读取（MMA 喂数的典型模式）：

| 布局 | cyc/LDS.u16 | shared 用量 |
|---|---|---|
| 裸 `[64][64]` | **32.00** | 8192 B |
| padding `[64][66]` | **1.00** | 8448 B (+3%) |
| XOR swizzle 8×8 | 4.00 | 8192 B (+0%) |

> 裸列读是 32-way 冲突，慢 32 倍。**padding 用 3% 的 shared 换来 32 倍加速，是最划算的优化**。XOR swizzle 在这个 8×8 粒度下只消到 4-way，但它零额外空间，且是 TMA/`ldmatrix` 唯一支持的布局——用 TMA 时没得选，手写 kernel 时优先 padding。

## C4 `m_cpasync` — 三种搬运方式

| 方式 | 带宽 |
|---|---|
| 手写 `ld.global` + `st.shared` | 2348 GB/s |
| `cp.async` 16B | 2371 GB/s |
| **`cp.async.bulk`（整块拷贝）** | **5423 GB/s** |

> `cp.async` 单看带宽和手写几乎一样（它的价值是**释放寄存器和发射槽**，让计算和搬运真正重叠）。而 **`cp.async.bulk` 比手写快 2.3 倍**——它是单线程发起的整块拷贝，绕开了 per-thread 地址计算。注意这还**不是真正的 TMA**（真·TMA 描述符路径见 C8）。Hopper 上吃满搬运带宽，cp.async.bulk / TMA 都不可省。

## C5 `m_pipeline` — cp.async 流水级数

| stages | GB/s |
|---|---|
| 1 (无流水) | 1768 |
| 2 | 2360 |
| 3 | 2742 |
| **4** | **2846** |
| 6 | 2872 (峰值) |
| 8 | 2859 |
| 12 | 2657 (shared 挤占 occupancy) |

朴素同步 global 读作为对照：2574 GB/s。

> **收益在 4 级饱和，6 级见顶，之后因为 shared 用量拖低 occupancy 反而倒退。** 常见的 cutlass 3~4 stage 默认值是有实测依据的。单级 cp.async 比朴素读还慢——没有流水就只有开销。

## C6 `m_dsmem` — Hopper 集群分布式 Shared Memory

`cudaOccupancyMaxPotentialClusterSize` = **8**。

| 访问目标 | cyc/LDS | B/clk/SM | 延迟 |
|---|---|---|---|
| 本地 shared | 1.00 | 127 | **29 cyc** |
| DSMEM (cluster=2) | 7.50 | 17.1 | 181 cyc |
| DSMEM (cluster=4) | 7.50 | 17.1 | 198 cyc |
| DSMEM (cluster=8) | 7.50 | 17.1 | 197 cyc |

> DSMEM 延迟是本地 shared 的 **6.5 倍**，带宽只有 **1/7.4**。但对比 L2 (295 cyc) 它仍快 **1.5 倍**，且**完全不占 L2 带宽**。定位很清楚：不是用来当大 shared 用的，而是替代"经 global 做 block 间交换"。集群规模对性能无影响（2 和 8 一样）。

# D. Tensor Core / 同步 / warp 原语 / 原子

## D1 `m_mma` — WMMA 实测吞吐

| 数据类型 | 形状 | 吞吐 |
|---|---|---|
| fp16, f32 累加 | m16n16k16 | 94.7 TFLOPS |
| fp16, f16 累加 | m16n16k16 | 95.0 TFLOPS |
| bf16, f32 累加 | m16n16k16 | 94.6 TFLOPS |
| tf32, f32 累加 | m16n16k8 | 35.6 TFLOPS |
| int8, s32 累加 | m16n16k16 | **140.9 TOPS** |

对照：FP32 CUDA core 满载 = 23.8 TFLOPS。

> **Tensor Core 是 CUDA core 的 4.0 倍**（fp16 vs fp32）。f16 累加相比 f32 累加**没有任何速度优势**（Hopper 上累加器精度免费），所以永远用 f32 累加。tf32 只有 fp16 的 37%，int8 是 fp16 的 1.5 倍。94.7 是 WMMA 同步路径成绩，`wgmma` 异步路径还能更高。

## D2 `m_barrier` — 同步开销（cycles/次）

| 原语 | 32 thr | 256 thr | 1024 thr |
|---|---|---|---|
| `__syncwarp()` | 1 | 2 | 9 |
| `__syncthreads()` | 15 | 29 | **77** |
| `bar.sync` 具名 barrier | 27 | 41 | 89 |
| `__threadfence_block()` | 12 | 19 | 120 |
| `mbarrier` (Hopper) | 71 | 90 | 218 |
| `__threadfence()` | 277 | 287 | **474** |

> 换算：一次 `__syncthreads()` (256 线程) ≈ **24 条 FFMA**；一次 `__threadfence()` ≈ **240 条 FFMA**，比一次 HBM 访问还贵。`__syncwarp()` 基本免费。`mbarrier` 比 `__syncthreads()` 贵 3 倍——它的价值在于**异步**（配合 TMA 做 producer/consumer），单纯当 barrier 用是亏的。

## D3 `m_warpprim` — warp 级原语

| 原语 | cyc/op (单 warp) | IPC/SM | 相对 IADD |
|---|---|---|---|
| IADD (基线) | 0.43 | 20.6 | 1.0x |
| `__shfl_xor_sync` | 6.0 | 1.00 | 20.6x |
| `__shfl_down_sync` | 9.1 | 1.00 | 20.7x |
| `__shfl_sync` (idx) | 10.5 | 0.90 | 22.8x |
| `__ballot_sync` | 8.6 | 0.63 | 32.5x |
| **shared 内存交换** | 8.1 | 0.50 | **41.2x** |
| `__any_sync` | 10.9 | 0.48 | 42.8x |
| `__match_any_sync` | 13.6 | 0.50 | 41.4x |
| `__reduce_add_sync` | 40.4 | 0.50 | 41.2x |

> **shuffle 比走 shared 做同样的 warp 内交换快 2 倍**（IPC 1.00 vs 0.50），且不占 shared、不需要 barrier。`__shfl_xor` 是最快的变体，蝶形 reduce 应该用它。`redux.add` 硬件指令延迟高达 40 cyc，只在需要跨整 warp 归约时才比 5 次 `shfl_xor` 划算。

## D4 `m_atomic2` — 原子操作冲突度曲线

79872 个线程同时打 N 个不同地址：

| 唯一地址数 | global (Gop/s) | shared (Gop/s) | shared/global |
|---|---|---|---|
| 1 (全部同址) | **1.37** | **147.6** | 108x |
| 2 | 2.61 | 282 | 108x |
| 4 | 5.22 | 520 | 100x |
| 8 | 12.7 | 893 | 71x |
| 16 | 13.1 | 1398 | 107x |
| 32 | 12.4 | 1913 | 154x |
| 256 | 26.6 | 1920 | 72x |
| 1024 | 102 | — | — |
| 65536 | **402.6** | — | — |

带返回值 vs 不带返回值：**几乎无差异**（1.37 vs 1.37, 402 vs 363）。

> **全局原子的同址冲突是灾难：1.37 Gop/s，比无冲突慢 294 倍。** 而 shared 原子在同址下仍有 147 Gop/s，比全局原子快 **108 倍**。所以直方图/归约的标准范式就是：**先在 shared 里聚合，每 block 只往 global 打一次**。另外 shared 原子在 32 地址后饱和（正好是 32 个 bank）。

## B6 `m_reg` — 寄存器压力与溢出（register spilling）

用 32 条独立 FMA 链强制高寄存器占用，再用 `__launch_bounds__(256, MINB)` 要求至少 MINB 个 block 同驻一 SM：

| MINB | 寄存器/线程 | 溢出 | 本 kernel 吞吐 | 相对 MINB=1 |
|---|---|---|---|---|
| 1 | 40 | 0 | 34.5 TFLOP/s | 1.00x |
| 2 | 40 | 0 | 34.5 | 1.00x |
| 4 | 40 | 0 | 34.5 | 1.00x |
| 8 | 32 | 168 B spill | 5.6 TFLOP/s | **0.16x** |

> MINB=8 即 64 warp/SM（H20 满占用），寄存器文件被压到每线程 32 个，低于 kernel 想要的 40 个，**8 个累加器溢出到 local memory（即 HBM）**，吞吐暴跌 6.2 倍。结论反直觉：**盲目拉满占用率会反噬**——寄存器不够时，高占用迫使溢出，比“低占用 + 全寄存器”慢得多。寄存器是 shared 之外第二大占用率限制因素（见 B1）。

## C7 `m_l1` — Hopper L1 / Shared 256KB 可配置切分（opt-in）

每个 SM 的 256KB 在 L1 data cache 与 shared memory 之间分配。默认每块只能用 **48KB** shared，余下 ~208KB 是 L1；通过 `cudaFuncAttributeMaxDynamicSharedMemorySize` opt-in 可把 shared 提到 **227KB**（此时 L1 只剩 ~29KB）。

| opt-in | 32KB | 64KB | 100KB | 164KB | 200KB | 227KB |
|---|---|---|---|---|---|---|
| OFF（默认） | OK | FAIL | FAIL | FAIL | FAIL | FAIL |
| ON | OK | OK | OK | OK | OK | OK |

> Hopper 上 **L1 与 shared 共享同一块 256KB**，并非独立两块。GEMM 想要大 shared tile（如 228KB）必须显式 opt-in，否则只能拿 48KB，直接限制 tile 大小与 occupancy。L1 缩小则 L2 命中率下降——这是“shared 换 L1”的硬权衡。

## C8 真·TMA 描述符拷贝 与 WGMMA 异步 Tensor Core（概念，本仓库未实测）

前面 C4 的 `cp.async.bulk`（5423 GB/s）是普通整块拷贝；Hopper 真正的两张王牌都依赖**描述符**，本机 CUDA 12.1 没有运行时编码 API（`cudaTensorMapEncodeTiled` / WGMMA 描述符），手搓易崩且与版本强相关，故未在此微基准实测，结论以 CUTLASS 3.x 为准：

- **真·TMA（`cp.async.bulk.tensor`）**：用 tensor-map 描述符描述 box 维度与 stride，单线程发起整块拷贝，**支持 multicast（一次写多个 cluster CTA）与 swizzle（按 MMA 需要的布局直接落 shared）**。吞吐与 cp.async.bulk 同量级（~5.4 TB/s），但彻底解放地址计算 / 发射槽，让“搬运”与“计算”真正解耦重叠——这是 Hopper GEMM 的数据路径。
- **WGMMA（`wgmma.mma_async`）**：warpgroup（4 warp = 128 线程）级**异步** Tensor Core，无需 `__syncthreads` 即可与 TMA、其他 MMA 重叠。原始 TFLOP/s 与 WMMA（D1，~94.7 fp16）基本持平，**真正收益是异步重叠**（compute-compute / compute-copy），需完整 GEMM 流水才能体现——这正是 CUTLASS 3.x `KernelSchedule` 在做的事。

## 写微基准的四个坑（本仓库全部踩过）

1. **死代码消除**：累加结果不写回 global 就会被整段删掉，表现为耗时 ≈ 0 或数字离谱大。务必写进 `out[]`，必要时加 `asm volatile("":::"memory")`。
2. **ptxas 会把循环不变的 shared load 提出去**：测 shared 必须用 `ld.volatile.shared`，否则 32-way bank conflict 也会显示成 1 cycle。
3. **测吞吐要打断依赖链，测延迟要构造依赖链**：同一段代码 ILP=1 和 ILP=4 差 3.4 倍，搞错了测出来的是另一个量。
4. **窄化截断**：`o[tid] = (int)(x0+x1+x2+x3)` 会让编译器发现 64 位高位无用，把 64 位乘法降级成 32 位（i64mul 从 1.9x 的假象变成真实的 7.7x）。必须按原类型写回。

# 附录 A：`__threadfence` 与 CUDA 内存模型

`__threadfence()` 是**内存栅栏**，不是同步 barrier —— 最容易混淆的一点。

| | `__syncthreads()` | `__threadfence()` |
|---|---|---|
| 语义 | **等所有线程到齐**（执行同步） | **不等任何人**，只约束本线程的写**顺序** |
| 作用域 | block 内 | 整个 GPU (device scope) |
| 保证 | 到齐 + 隐含 block 内 fence | 栅栏前的写，对他人一定先于栅栏后的写可见 |

`__threadfence()` 执行完线程立刻继续跑，它只承诺：**别人看到我栅栏后的写时，一定也能看到我栅栏前的写**。

## 三个作用域级别（本仓库 `m_barrier` 实测）

| 级别 | 一致性点 | 64 thr | 1024 thr |
|---|---|---|---|
| `__threadfence_block()` | block 内 / L1 | 12 cyc | 120 cyc |
| `__threadfence()` | 整个 GPU / **L2** | **277 cyc** | **474 cyc** |
| `__threadfence_system()` | host + peer GPU | 更贵（未测） |

**为什么 device scope 贵 23 倍**：L2 是 GPU 上所有 SM 的一致性点。`__threadfence()` 必须把本线程所有 pending 的写从 L1 / 写合并缓冲**刷到 L2 并等确认**；`__threadfence_block()` 只需刷到 L1/shared 层级。

### 典型用法：device-scope 生产者 / 消费者

```cpp
// 生产者线程
data[i] = result;     // 1) 先把数据写好
__threadfence();      // 2) 保证 data 落到 L2 之后，flag 才可能被别人看到
flag = 1;             // 3) 再置位“完成”标志

// 消费者线程
while (flag == 0);    // 自旋等待
// 读到 flag==1 的瞬间，data[i] 一定已经是最终值（fence 保证了写顺序）
```

⚠️ 两个坑：

- **它不保证原子性**：多个线程对同一个地址写，照样互相覆盖，`__threadfence()` 管不了竞争，要用 `atomicAdd` / `atomic_ref` 这类原子操作。
- **它不保证对方“看到”**：fence 只定**顺序**，不负责通知、不负责轮询。别人没看到你的写，纯粹是你没去等 / 没去读，不是 fence 的锅。要做可靠的跨线程信号，得自己配 `flag + 自旋`（如上），或用 `cuda::atomic_ref` 的 acquire/release。

**现代写法**：直接用 `cuda::atomic_ref<T, cuda::thread_scope_device>` 配 `memory_order_release`（生产者）/ `memory_order_acquire`（消费者），把“写顺序”和“读可见”一次性交给原子语义，比手写 `__threadfence() + flag` 安全且不易写错。

### 换算成直觉

一次 `__threadfence()`（device scope，277 cyc）≈ **62 条依赖链 FFMA**（按 4.45 cyc/条）或 277 条独立 FFMA；它比一次 HBM 访问（335 cyc）便宜一点点，但**同量级**——也就是说，一次设备级栅栏的开销已经接近一次远内存访问，能不用就不用，跨 block 通信优先走 shared / cluster DSMEM / `__threadfence_block()`（12~120 cyc）这种便宜得多的层级。

`__threadfence_block()`（12~120 cyc）才是“block 内生产者/消费者”该用的；只有确认真的要和别的 block / 别的 SM 协调全局可见性时，才上 device scope 的 `__threadfence()`。

### 四把尺子

整套实验只用四种测量手段，每个结论至少由其中两把尺子交叉验证：

1. **`cudaEvent` 计时** — 测带宽。设备时钟域，不受主机抖动影响。
2. **`clock64()`** — 测延迟。必须配真串行的指针追逐（下一跳地址依赖上一跳读回的值），否则测到的是吞吐不是延迟。
3. **NVML 每链路字节计数器** — 测**线上真实字节**。这是本章最关键的工具：
   - `Data Tx/Rx` = 协议净荷，实测与 payload 精确相等（发 4295.0 MB 数到 4295.0 MB），可以当净荷标尺用；
   - `Raw Tx/Rx` = 线上总字节（净荷 + 包头 + 流控 flit + idle）；
   - 计数器是**每条 link 独立**的，这一点让 F5 的条带粒度实验成为可能。
4. **inline PTX** — 精确控制指令形态（`st.global.v4` / `ld.volatile` / `ld.global.cv` / `red` vs `atom` / `multimem.*`），
   避免编译器把远端访存优化掉或改变语义。

### 一条重要的方法学警告：Raw 计数器包含 idle

`nv06` 的数据暴露了一个陷阱。看这一列：

| 负载 | 有效带宽 | payload | rawTx | **rawTx 速率** |
|---|---|---|---|---|
| 大块顺序写 | 370.2 GB/s | 740613 MB | 837550 MB | **418.6 GB/s** |
| 4B 离散写 | 35.0 GB/s | 70093 MB | 846209 MB | **422.5 GB/s** |
| 4B 原子 | 37.8 GB/s | 75737 MB | 837812 MB | **418.1 GB/s** |
| memcpyPeer | 391.1 GB/s | 782221 MB | 832453 MB | **416.0 GB/s** |

有效带宽从 35 变到 391（11 倍），**rawTx 速率却纹丝不动，恒在 416–423 GB/s**。
结论很明确：**Raw 计数器统计的是线路占用，方向一忙就顶到 ~420 GB/s 的天花板，空闲 flit 也计入**。

所以「用 `raw/payload - 1` 反推每包头字节数」的做法是**不成立**的（`nv06` 里那张推出 33.5 B/包的表就是这么错的）。
Raw 计数器的正确用法只有两个：

- **判断某个方向有没有非净荷流量**（比如写负载下 `dataRx=0` 但 `rawRx=972 MB`，证明反向全是纯协议包）；
- **给出线路占用上限**：~420 GB/s / 478 GB/s = 87.9%。

本章凡是用到 raw 的结论都按这个口径写。

## F1 带宽的顶：370 GB/s 是怎么来的

### 基线（256 MB，78×4 block）

| 路径 | GB/s | 相对理论 478 |
|---|---|---|
| 本地 HBM 写 | 3154 | — |
| 本地 HBM 读 | 2568 | — |
| **NVLink 远端写 GPU0→GPU1** | **370.2** | 77.4% |
| **NVLink 远端读 GPU0←GPU1** | **369.6** | 77.3% |
| Copy Engine `memcpyPeer` 0→1 | **391.1** | 81.8% |
| 双向对打（0→1 与 1→0 同时） | **730.9** | 1.97× 单向 |

逐对矩阵：0↔1、0↔2、0↔3、1↔2… 全部 ≈370 GB/s，**NVSwitch 完全对称**。

### 478 → 370 的差额拆解

```
478.1 GB/s   18 link × 26.562 GB/s 理论信令率
   ↓  ×0.879
~420   GB/s   Raw 计数器的线路占用上限（编码/成帧开销）
   ↓  ×0.882
370.2 GB/s   实测净荷（包头 + 反向 ACK 占用的额外线路时间）
   ────────
 总效率 77.4%
```

反向 ACK 的代价能单独量出来：`nv17` 在纯写负载下测到 `dataRx = 0` 而 `rawRx = 972.0 MB`，
折算**每个 128 B 写事务的 ACK 占用 ≈ 115.9 B 线上字节**。
而且把写宽度从 128 b 换成 32 b，`rawRx` 只差 0.55%——**ACK 开销由事务数决定，与写多宽无关**。

### Copy Engine 为什么反而更快

CE 比 SM 快 5.6%（391.1 vs 370.2），但两者的 `dataTx/payload` **都是 1.0000**。
净荷效率一模一样 ⇒ **CE 的优势不来自更省的包格式，而来自更好的请求流水**（没有 SM 的发射和调度开销）。

## F2 传输粒度：写 16 B，读 32 B（不对称！）

这是本章最硬的一组发现，由**三个独立构造**交叉验证，全部基于硬件净荷计数器而非推测。

| 实验 | 构造 | 观测 | 推出 |
|---|---|---|---|
| `nv03_stride` | 4B 访问，stride ≥128 B | `dataTx/payload = 4.000` | 写粒度 = 4×4 B = **16 B** |
| `nv03_stride` | 同上 | `dataRx/payload = 8.000` | 读粒度 = 8×4 B = **32 B** |
| `nv05_partial_write` | 只写每 128B 块的前 C 字节 | C=1/2/4 三行 `dataTx` **完全相同**（280700 MB） | 写量子 = **16 B** |
| `nv05_partial_write` | C=16/32/64/128 | `dataTx/有用 = 1.00`（无浪费） | 写满 16 B 后**不再放大**，也**不是整 128 B 写** |
| `nv04_coalesce` | 每 line 只放 16 B 有用数据（L=8） | `dataTx/payload = 1.000` | 独立验证写粒度 = 16 B |
| `nv04_coalesce` | 每 line 只放 4 B（L=32） | `dataTx/payload = 4.000` | 16/4 = 4×，与 nv03 一致 |
| `nv06_wire_overhead` | 4B 离散写 / 读 | 4.0000 / 8.0000 | 再次确认 16 B / 32 B |

**读粒度是写粒度的 2 倍**，这个不对称是 NVLink 的一个基本性质：
读必须按 32 B sector 整取，写可以按 16 B 量子部分提交（带 byte-enable）。

### 没有 read-modify-write

`nv05` 的 8 行数据里 **`dataRx` 严格等于 0**（不是小值，是 0）。
如果远端写不满一个 sector 时需要把它读回来合并，Rx 方向必然出现同量级净荷。
所以：**远端写 = posted + write-through + 16 B 粒度 byte-enable，没有 RMW 往返**。

### 带宽阶梯完美印证 16 B 量子

`nv05` 中 C=1→2→4 的有效带宽是 8.8 → 17.5 → **35.1 GB/s**，精确 2× 阶梯——
因为线上搬的字节恒定（都是 16 B），有用字节翻倍则有效带宽翻倍。C=16 之后饱和，拐点正好在 16 B。

### 合并只在 SM 的 LSU 里做，链路侧不做二次合并

`nv04` 固定每 warp 搬 128 B 有用数据，只改「散布到几条 line 上」：

| 散布度 L | 远端写 GB/s | 相对 L=1 | `dataTx/payload` |
|---|---|---|---|
| 1（全在一条 line） | 358.3 | 1.00× | 1.000 |
| 2 | 328.7 | 1.09× ↓ | 1.000 |
| 8（每 line 16 B） | — | — | 1.000 |
| 32（每 line 4 B） | **35.0** | **10.24× ↓** | 4.000 |

带宽掉 **10.24×** 而净荷只放大 **4.00×**，差出 2.6 倍。
说明散射的瓶颈**不只是字节浪费，更是请求条数**——一条指令产生 32 个独立请求，
受限于 LSU/L2 的请求发射速率。合并窗口就是**一条指令内 warp 的 32 个 lane 地址**，不跨指令、不跨 warp。

### 跨 128 B 边界的访问被拆成 2 个传输

`nv07` 做了一个控制变量极干净的对照：每线程搬 8 B（2 条 `st32`），warp 内 lane 地址**保持连续**，
唯一变量是整体偏移 delta。`delta=0` 时每个 8 B 都自然对齐；`delta=4` 时**恰好每 16 个线程有 1 个**
骑在 128 B 边界上。两者指令数、合并度完全相同。

| delta | 跨界比例 | 远端写 GB/s | `dataTx/payload` |
|---|---|---|---|
| 0 | 0 | 320.9 | 1.107 |
| 4 | **1/16 = 6.25%** | 270.0（**0.841×**） | **1.183** |

净荷放大从 1.107 升到 1.183，**增加 +6.9%**；而构造上跨界比例正好是 **6.25%**，
每个跨界访问多产生 1 个传输 ⇒ 预测 +6.25%，**实测 +6.9%，吻合到 0.65 个百分点**。
⇒ **拆分边界 = 128 B**。

但**带宽代价（−15.9%）远大于净荷代价（+6.9%）**，又一次印证「瓶颈是请求条数不是字节」。

排除性对照：**本地 HBM 呈现完全相同的模式**（本段本地写 3072.0 → 2163.3，0.704×，
下降幅度甚至比远端更大）⇒ 跨边界拆分发生在 **SM/L2 侧的地址处理**，
NVLink 只是把已经拆好的请求原样搬过去，**不是 NVLink 特有行为**。

基址偏移扫描（`st32`，4 B 访问）显示对齐到 **32 B** 就能基本恢复性能（0.914 vs 最差 0.682），
与读粒度 32 B 自洽。而 16 B 访问（`st128`）因硬件强制自然对齐，对基址偏移基本不敏感（最差 0.929）。

### 指令宽度本身不重要

`nv02` 扫每线程访问宽度：只要 warp 内完全合并，**W 从 16 B 降到 4 B 几乎不掉带宽**（368.9 → 361.0，−2.1%）。
W=1 B 时远端掉到 0.722×，但**本地掉得更狠（0.484×）**——
这条排除性对照证明 1B/2B 的损失主要来自 **SM 侧发射率**，不是 NVLink 线上粒度。

> **可操作结论**：跨卡访存优化的第一优先级是**保证 warp 内合并**，而不是加宽单线程访问指令。
> 合并度掉一档，带宽掉一个数量级。

## F3 缓存层级：发起侧只进 L1，目标侧 L2 照常服务

`nv34` 用「普通 `ld`（可缓存）」与「`ld.global.cv`（强制绕过）」两条曲线相减，把缓存效应和 TLB 效应分开：

| 页数 N | working set | 本地 cached | **远端 cached** | 本地 bypass | **远端 bypass** |
|---|---|---|---|---|---|
| 1 | 128 B | 41 | **41** | 297 | 1616 |
| 1024 | 128 KB | 41 | **41** | 291 | 1603 |
| 2048 | 256 KB | 167 | 1120 | 292 | 1606 |
| 4096 | 512 KB | 293 | **1608** | 293 | **1608** |
| 8192 | 1 MB | 294 | 1610 | 294 | 1610 |

（单位 cycle @ 1.98 GHz）

两条决定性证据：

1. **N ≤ 1024 时远端 cached = 41 cyc，和本地 L1 命中一模一样** ⇒ peer 数据确实躺在 GPU0 的 L1 里。
2. **N = 4096 时远端 cached = 1608，与远端 bypass 的 1608 完全相等** ⇒ L2 一次都没命中。
   而同样 N 下本地 cached = 293 = L2 命中延迟（working set 才 512 KB，塞进 60 MB 的 L2 绰绰有余）。

**结论：NVLink peer 内存的可缓存层级只到 L1（256 KB/SM），本地 L2 对它完全透明。**
跨卡访问的数据复用窗口只有 L1 那么大——这条对算法设计的约束比带宽数字重要得多。

配套结论：

- **L1 有效容量 ≈ 128–256 KB**（N=1024 全命中，N=2048 开始失效，解出命中率 50%）。
- **远端 TLB reach ≥ 16 GB，量程内无台阶**：远端 bypass 从 2 MB 覆盖到 16 GB 一路平在 1586–1616 cyc（±2%）。
  「远端访问要多交一份地址翻译税」在这个量程上**不成立**。
- **peer 映射槽位在 1024 块独立分配内不会耗尽**：K=1→1024 延迟平在 1559–1615 cyc，无跳变。
- **打散映射对带宽基本无损**：1 块连续 1 GB 是 370.8 GB/s，512 块独立 2 MB 是 371.1 GB/s。

### 三个实验的交叉验证，以及一处表面矛盾的澄清

`nv14` / `nv15` / `nv34` 三个实验独立测了这件事，初看结论打架，**必须换算到同一坐标才能对齐**。

`nv15` 给出的是**决定性的计数器证据**：4 MB 的远端 buffer 读 64 遍，
NVLink 线上 `dataRx` 只有 **1.00×** buffer 大小而不是 64×
（`ld.volatile` 阳性对照组则精确给出 64×）。缓存确实存在，这一点无可辩驳。

但 `nv15` 把它归给了 L2，这一步不成立。三份数据换算成**触及的 cache line 条数**之后完全一致：

| 实验 | 表述 | 换算成 line 数 | 延迟 |
|---|---|---|---|
| nv15 | WS = 4 MB（4 KB 步长） | 1024 | 39.1 cyc |
| nv34 | N = 1024 页（2 MB 步长） | 1024 | 41 cyc |
| nv15 | WS = 16 MB | 4096 | 1248.8 cyc |
| nv34 | N = 4096 页 | 4096 | 1608 cyc |

**两者拐点完全相同，都在 1024→4096 条 line 之间，即 128 KB→512 KB。**
`nv15` 的「WS 尺寸」量的是地址跨度，不是驻留字节数——用 4 KB 步长追指针时，
4 MB 的 WS 只触及 1024 条 line、共 128 KB，这个量正好是一个 SM 的 L1 装得下的。

**判定归 L1 而非 L2 的决定性一条**是 `nv34` 的 N=4096 行：单线程、512 KB 驻留，
远端 cached = 1608 cyc，与远端 bypass 的 1608 **完全相等**。
512 KB 塞进 60 MB 的 L2 绰绰有余，如果 L2 缓存 peer 数据，这里必须出现 ~290 cyc 的 L2 命中。它没有。
单线程测试只用到一个 SM 的 L1，而 L2 是全卡共享的——所以这一行干净地把 L1 和 L2 分开了。

`nv15` 的带宽曲线反过来印证了「聚合 L1」的解释：

| WS | `ld.global` GB/s | 解释 |
|---|---|---|
| 4 MB | **7137.2** | 每个 block 的分片都在自己 SM 的 L1 里 |
| 16 MB | 3299.1 | 开始超出聚合 L1，部分回落到 NVLink |
| **32 MB** | **396.0** | 基本等于 NVLink 线速，缓存失效 |
| 256 MB | 368.7 | 纯 NVLink |

失效点落在 **16→32 MB** 之间，而 78 SM × 256 KB = **19.5 MB 聚合 L1**，正好落在这个区间。
若真是 60 MB 的 L2 在缓存，32 MB 那一档不可能掉到 396 GB/s。

**统一结论**：peer 内存**会**被缓存，但只到 **L1**；本地 L2 对 peer 地址完全透明。
单个 SM 的复用窗口是 256 KB，全卡聚合复用窗口约 19.5 MB。

`nv14` 的延迟层级分解与此自洽，并独立复现了 NVLink 净往返代价：

| 层级 | cycles | ns |
|---|---|---|
| L1 命中 | 38.8 | 19.6 |
| L2 命中 | 69.2 | 35.0 |
| 本地 HBM | ~287 | ~145 |
| **远端 NVLink** | **1583** | **799** |
| **HBM→remote 增量** | **1301.8** | **657.5** |

657.5 ns 与 `nv34` 独立算出的 656 ns **吻合到 0.2%**。

`nv14` 还发现 **cache modifier 的作用是二值的、不是渐进的**：
`.cg` / `.lu` / `.cv` / `volatile` 在远端小 WS 下全是 ~1580 cyc，
而 `ld.global` / `.ca` / `.cs` / `.nc` 全是 38.8 cyc，**差 1542 cyc**。
前四个强制请求下推、绕过本地缓存，后四个允许 L1 命中，中间没有过渡态。
（`.cs` streaming 在大 WS 下略快 47.9 cyc，因为省了一次 LRU 插入决策。）

### 但是**远端那张卡的 L2 会命中**——这是另一回事

本地 L2 不缓存 peer 地址，不代表请求到了对面不查 L2。`nv16` 专门测了这一条，
自变量只有一个：**GPU1 侧 L2 的冷热**（在 GPU1 上预读 WS = warm / 冲刷 256 MB = cold）。
为了不让 GPU0 的本地缓存污染结果，GPU0 侧**一律用 `ld.global.cv`** 并每次先冲刷自身 L2。

| GPU1 WS | warm (cyc) | cold (cyc) | **cold − warm** |
|---|---|---|---|
| 1 MB | 1583.7 | 1583.6 | −0.0 |
| 4 MB | 1582.9 | 1621.5 | +38.6 |
| 16 MB | 1582.7 | 1850.2 | +267.5 |
| **32 MB** | 1584.3 | 1890.4 | **+306.1** |
| 64 MB | 1698.1 | 1892.6 | +194.5 |

**远端 L2 命中比远端 HBM 省 306 cyc = 155 ns。** 本地对照组（32 MB：283.4 vs 677.2，差 393.9 cyc）
证明「焐热/冲刷」手法本身有效，且远端省下的 306 略小于本地的 394，
符合「远端 L2 命中省掉的是 GPU1 侧的 HBM 时间，NVSwitch 往返固定不变」这一模型。

于是得到**完整的远端读延迟分解**：

| 路径 | cycles | ns |
|---|---|---|
| 远端 **L2 命中** | **~1583** | **800** |
| 远端 **HBM** | **~1890** | **955** |
| └ 其中 NVSwitch+NVLink 往返 | ~1300 | ~657 |
| └ 远端 L2 查询 | ~280 | ~141 |
| └ 远端 HBM 额外 | ~306 | ~155 |

两条推论：

- **800 ns 是硬地板**。warm 列在 1 MB→32 MB 全程锁死在 1582.7–1584.3，
  即使对面 L2 全命中也降不下来 ⇒ `nv14` 拆出的 1302 cyc「NVLink 往返」与远端缓存状态**完全无关**。
- **带宽完全不受远端 L2 冷热影响**（9 个 WS 档 warm/cold 比值全在 1.00–1.05×）。
  流式读在 370 GB/s 已被线速卡住，远端 L2 省的是延迟，而延迟早被并发隐藏了。

> 合起来看，缓存模型是**不对称**的：
> **发起侧只有 L1 能缓存 peer 数据（256 KB/SM，聚合 19.5 MB）；
> 目标侧的 60 MB L2 会正常参与服务，但只影响延迟不影响带宽。**

## F4 延迟：800 ns 的往返，和它的每一段

| 层级 | cycles | ns | 说明 |
|---|---|---|---|
| 本地 L1 命中 | 41 | 21 | |
| 本地 L2 命中 | ~290 | 146 | |
| 本地 HBM | 315 ~ 665 | 159 ~ 336 | 取决于测法与 row-buffer 命中 |
| **远端读（流水，下界）** | **1583–1616** | **~800** | `nv14` / `nv34` 连续指针追逐 |
| **远端读（完全暴露，上界）** | **1849** | **934** | `nv18` 每次采样被 `clk()` 夹断 |
| 远端读 p99 | ~2300 | ~1160 | 延迟敏感场景按这个预算 |

**净 NVLink+NVSwitch 往返代价 = 远端 − 本地 L2 = ~1300 cyc = 656 ns。**

### NVSwitch 三个 peer 完全对称

`nv18` 对 0→1 / 0→2 / 0→3 各采样 4096 次：p50 = **1849 / 1858 / 1850** cyc，
极差 **9 cyc = 4.5 ns = 0.49%**，小于单次 `clk()` 的开销（7 cyc），在测量分辨率内不可区分。

### 远端的抖动反而比本地小

| | p50 | stddev | **p99/p50** |
|---|---|---|---|
| 本地 HBM | 665 | 154.2 | **1.70** |
| 远端 NVLink | 1849 | 137.7 | **1.24** |

远端不但相对抖动更小，**绝对 stddev 也更低**。
原因：本地 HBM 呈**双峰分布**（510–590 占 37.0%，672–752 占 32.6%，相距约 160 cyc，
对应 DRAM row-buffer hit / page conflict）；而远端 1849 cyc 里约 1300 cyc 是 NVLink/NVSwitch 的
**确定性传输时间**，把 DRAM 侧的双峰结构平滑成了单峰右偏。

## F5 18 条 link 怎么分流量：条带粒度 = 256 B

这是本章唯一一个**直接观测硬件内部分配规则**的实验，靠的是 NVML 的**每链路独立计数器**。

方法：把写限制在一个大小为 W 的地址窗口内反复写（总 payload 固定 2 GB，只改 W），
数有几条 link 被点亮。

| 窗口 W | 活跃 link | 变异系数 CV | 点亮的 link 编号 |
|---|---|---|---|
| **256 B** | **1** | 4.123 | 0 |
| **512 B** | **2** | 2.828 | 0,1 |
| 1 KB | 4 | 1.871 | 0,1,**8,9** |
| 2 KB | 6 | 1.541 | 0,1,8,9,**16,17** |
| 4 KB | 10 | 0.984 | 0,1,2,3,8,9,12,13,16,17 |
| **8 KB** | **18** | 0.354 | 全部 |
| 128 KB | 18 | 0.053 | 全部 |
| 4 MB | 18 | **0.016** | 全部 |

**结论**

1. **地址→link 条带粒度 = 256 B**。W=256 B 只点亮 1 条，W=512 B 恰好 2 条。
   若粒度是 128 B，W=256 就该点亮 2 条；若是 512 B，W=512 仍只该点亮 1 条。只有 256 B 同时满足这两行。
2. **映射是 hash，不是顺序轮转**。W=1 KB 点亮的是 {0,1,**8,9**} 而不是 {0,1,2,3}。
   且 link 恒**成对**出现（每对两条数值完全相同），说明最低位那一级是 2 路对分。
3. **要用满 18 条 link，地址跨度至少 8 KB**（32 个 256 B 块）；
   要拿到接近理想的均衡（CV<0.06）需要 **≥128 KB**。
4. **18 条 link 完全聚合共享，不按目标静态划分**。
   发给 GPU1/2/3 的 per-link 分布**逐条一致**（119.5 / 119.2 / 119.2…），
   同时发给 3 个目标时每条 link 的量正好变 3 倍（358.6 ≈ 3×119.5）。
5. 大范围顺序写时 18 条 link 的 **CV = 0.001**，负载均衡近乎完美。

> **这条解释了一个长期困扰人的现象**：小消息 P2P 带宽上不去，主因**不是延迟，是物理链路根本没被点亮**。
> 一个 4 KB 的 P2P 传输最多只能用到 10/18 = 56% 的链路；512 B 的只能用 2/18 = 11%。

## F6 并发度与在途容量

### 每线程在途上限 = 4（而且不是 NVLink 的锅）

`nv08` 让单线程连发 K 个互不依赖的远端 load：

| K | 远端 LOAD cyc/iter | 本地 LOAD cyc/iter |
|---|---|---|
| 1 | 1660.4 | 315 |
| **4** | **1730.7**（+4%） | **381.0** |
| 8 | 5014.7（2.9×） | 980.6 |

**远端和本地在完全相同的 K=4→8 处拐弯** ⇒ 这 4 个槽位是 **LSU/MSHR 的通用上限，不是 NVLink 专属**。

### 远端 store 不受槽位限制，受固定发射节流

远端 STORE 从 K=4 到 K=128，`cyc/请求` **恒为 19.85–19.99**，没有任何平台段。

- 19.99 cyc @ 1.98 GHz = 10.1 ns/warp 事务（512 B）⇒ **单 warp 远端写天花板 = 50.7 GB/s**
- 本地对照 15.99 cyc ⇒ **NVLink 写路径每事务多 4.0 cyc = 2.0 ns 固定开销**，带宽比 50.70/63.37 = **80.0%**

### 单 SM 的远端写出口 = 50.5 GB/s，2 个 warp 就打满

`nv09` 把 kernel 锁在 `grid=1`（单 SM），扫 warp 数：

| warps | 远端写 GB/s | 本地写 GB/s | 远端读 GB/s |
|---|---|---|---|
| 1 | 25.81 | 25.93 | 0.61 |
| **2** | **50.42** | 51.73 | 1.21 |
| 4 | 50.41 | **63.01** | 2.43 |
| 8 | 50.44 | 63.00 | 4.85 |
| 32 | **50.43** | 63.01 | 19.35 |

**16 倍的 warp 数换来 0.02% 的带宽变化。** 这不是延迟掩盖不足，
而是 SM 到 NVLink 的写路径上有一个**固定宽度的串行化出口**。
它与 `nv08` 的 19.99 cyc/事务（512 B/10.1 ns = 50.7 GB/s）**同一个数**，两个独立构造互证。

而且这个出口是**远端专属**的：同一段代码的本地写在 4 warp 继续涨到 **63.01** 才停
⇒ 50.4/63.0 = **80.0%**，与 `nv08` 算出的 80.0% 完全一致。

### 两个瓶颈的交接点在 7.4 个 SM

`nv10` 用 `block=1024`（32 warp/SM）对照 `block=256`（8 warp/SM）扫同样的 grid，
这是区分「SM 数不够」和「每 SM 出口有限」的判决性实验：

| grid | 远端写 GB/s | **每 SM** | %of 370 | block=1024 对照 |
|---|---|---|---|---|
| 1 | 50.64 | 50.64 | 13.7% | 50.45（**1.00×**） |
| 4 | 202.17 | 50.54 | 54.6% | 202.17（**1.00×**） |
| **6** | 302.53 | **50.42** | 81.8% | — |
| 8 | 312.90 | 39.11 | 84.6% | 311.33（**1.00×**） |
| 12 | 364.58 | 30.38 | 98.5% | — |
| **16** | **373.48** | 23.34 | **100.9%** | 372.57 |
| 78 | 369.99 | 4.74 | 100.0% | 371.05 |
| 312 | 370.62 | 4.75 | 100.2% | — |

1. **grid=1..6 的每 SM 值离散度只有 0.4%**（50.64/50.60/50.56/50.54/50.42）——完美线性。
2. **把每 SM 的 warp 数从 8 提到 32（4 倍），带宽一点不变（全是 1.00×）**
   ⇒ 少 SM 时的限制确实是**每 SM 的固定出口**，加 warp 无用。
3. grid≥16 后加 SM 也无用 ⇒ 此时换成**共享的 link 侧**限制。
   两个瓶颈在 **grid ≈ 373/50.5 = 7.4** 处交接。

⇒ **喂饱 NVLink 写只要 16/78 = 20.5% 的 SM。** 而本地 HBM 写要 60 个 SM 才饱和于 3597 GB/s。
**远端场景下有 62 个 SM 的访存能力是闲置的**——这是 NVLink 应用最核心的资源约束。

**读则完全相反**：`nv09` 的 rem_RD 列要到 grid=156（2 个 wave）才有 364 GB/s，
grid=78 时只有 282.7（76%）。因为每线程只能挂 4 个在途 load（`nv08`），
读的并发度只能靠线程数堆；而写是 fire-and-forget，8 个 SM 的发射能力就够。

### 没有拥塞崩溃

grid 从 16 一路过饱和到 312（**19.5 倍**），远端写在 361.91 ~ 373.48 之间波动，**极差仅 3.1%**，
末端 370.62 与峰值 373.48 基本持平，无任何下降趋势。
⇒ **NVLink 是基于 credit 的无损背压**：过量请求在 SM 侧排队等待，不丢弃、不重传，
所以不会出现 TCP 式的拥塞崩溃。

### Little's Law：在途容量收敛到 769.6 KB

`nv11` 在每个并发度上**同时**测吞吐 λ 和探针延迟 W，算在途字节 λ×W：

| grid | 线程数 | BW GB/s | 延迟 ns | **在途字节** | 折算 128B 请求 | 每 link |
|---|---|---|---|---|---|---|
| 1 | 256 | 50.64 | 11293 | 571 906 | 4468 | 248 |
| 4 | 1024 | 202.18 | 3535 | 714 744 | 5584 | 310 |
| **16** | **4096** | **373.38** | 2139 | 798 484 | 6238 | 347 |
| 64 | 16384 | 370.59 | 2168 | 803 234 | 6275 | 349 |
| 312 | 79872 | 367.93 | 2183 | 803 279 | 6276 | 349 |

饱和区（11 个点）平均在途 = **788 037 B = 769.6 KB**，收敛得非常干净。

- 折算 128 B 请求 = **6157 个**，每条 link ≈ **342 个**
- 折算 256 B 请求 = 3078 个，每条 link ≈ 171 个

**这就是硬件能容纳的最大在途数据量（NVLink 的 BDP / credit 池容量）。**

配套结论：**16 个 block（4096 线程）就能打满 370 GB/s**，只占 78 SM 的 20%；
再往上加到 312 个 block 带宽纹丝不动（367.9），**没有拥塞崩溃**。

### 延迟随负载：95% 利用率之前只涨 1.3×

`nv12` 用两条 stream：一条跑可调强度的背景远端写，一条跑单线程 pointer-chase 探针
（探针 spin 等背景的 device flag，保证落在稳态里）：

| bg_grid | 背景带宽 GB/s | 利用率 | 探针延迟 ns | vs 空载 |
|---|---|---|---|---|
| 0 | 0 | 0% | 793.0 | 1.00× |
| 1 | 50.61 | 13.7% | 797.1 | 1.01× |
| 4 | 201.60 | 54.5% | 968.3 | 1.22× |
| **7** | **351.29** | **94.9%** | 1019.1 | **1.29×** |
| **8** | 312.05 | 84.3% | 1381.8 | **1.74×** ← knee |
| 16 | 372.06 | 100.6% | 1395.8 | 1.76× |
| 32 | 366.95 | 99.2% | 1948.1 | 2.46× |
| **78** | 368.96 | 99.7% | **5980.7** | **7.54×** |
| 312 | 369.43 | 99.8% | 6077.2 | 7.66× |

1. **利用率从 13.7% 涨到 94.9%（6.9 倍），延迟只涨 29%。**
   这是**深缓冲、弱背压**的特征，与 `nv11` 测出的在途池是纯 BDP 的 2.6 倍完全吻合。
2. **knee 的成因不是 link 饱和，而是 SM 侧超订。** 决定性证据：
   bg_grid=7 时带宽 351.29（94.9%）延迟 1.29×；bg_grid=8 时带宽反而**掉到** 312.05（84.3%），
   延迟却跳到 1.74×。**带宽更低而延迟更高，link 拥塞无法解释这个组合。**
   真正的原因是单 SM 出口只有 50.5 GB/s（`nv09`/`nv10`），7×50.5 = 353.5 已够喂满 link；
   到第 8 个 SM，探针所在的 block 开始和背景 block 抢**同一个 SM 的出口**。
3. **真正的延迟爆炸在 bg_grid=78（= SM 总数），7.54×。**
   此时带宽 368.96 与 bg_grid=48 的 366.03 几乎相同——再次证明与 link 利用率无关，
   而是探针**无处可逃**，每个 SM 都被背景占据。

> **可操作结论（本章最实用的一条）**：通信与计算重叠时，
> **把通信 kernel 限制在 ≤8 个 SM**（`grid<=8` 或用 stream priority 隔离）。
> 这样能拿到 95% 的 link 带宽，同时把其他 kernel 的远端访存延迟维持在 1.3× 以内。
> 铺满 78 个 SM 只多拿 5% 带宽（368.96 vs 351.29），却让延迟恶化 5.8 倍。

### 为什么没有直接测出 FIFO 深度：一个方法论死结

`nv13` 原计划用经典的 burst–sleep–burst 逐条采样法直接量缓冲深度，三种构造全部失败，
**这个失败本身是有信息量的**：

- **v1 单 warp store**：所有 (B,S) 组合间隔恒为 64 cyc，无 knee。
  单 warp 发射速率 = 512 B/64 cyc = **15.8 GB/s**，而后端排空 370 GB/s，
  **探测器比被测对象弱 23 倍，缓冲永远填不满。**
- **v2 多 SM store**：被自身数据证伪。算出的「发射速率」grid=1 是 146.8 GB/s、
  grid=32 是 **3972.6 GB/s**——超过全卡 370 GB/s 上限一个数量级，物理上不可能。
  根因：`st128` 是 fire-and-forget，无目的寄存器，`clock64` 与 store 完成之间**没有数据依赖**，
  记录 lane 可以跑在真实流量前面。测到的只是**指令发射槽间隔**。
- **v3 多 SM load + 强制依赖**（把返回值经 `and.b32 t,%1,0` 喂进 `clk()` 之前）：
  数据自洽了（稳态 1693.3 cyc = 855.2 ns，独立复现 `nv08` 的 838.6 ns，误差 2.0%），
  但**逐条明细完全平坦，S=0 与 S=10000 ns 几乎逐条相同**，无任何拐点。
  因为强制依赖之后并发度被压成 1，测到的是延迟不是深度。

> **死结**：让 `clock64` 可信所需的**数据依赖**，恰恰摧毁了填满缓冲所需的**并发度**。
> store 有并发但不可观测，load 可观测但无并发。
> **所以在途容量的数值一律引用 `nv11` 的 769.6 KB**——Little's Law 只需要聚合吞吐和平均延迟，
> 两者都能可靠测量，从而绕开了这个死结。

副产品（这两个数字本身可信）：单 warp 远端 store 发射速率 = **15.8 GB/s**
（解释了 `nv09` 里 1 warp 只有 25.8 GB/s 的现象）；B≤256 时 burst 对空闲时间 S 完全不敏感
（差异 <0.1%），因为 256×512 B = 128 KB **确实还没填满 770 KB 的池子**，与 `nv11` 自洽。

## F7 写的完成语义与 fence

### 发射 vs 完成，差 235 倍

| 操作（远端） | cycles | ns |
|---|---|---|
| 裸 `st.global`（发射） | **7.6** | 3.8 |
| `+ __threadfence_block()` | 25.1 | 12.7 |
| `+ __threadfence()`（device） | 593.8 | 300 |
| `+ __threadfence_system()` | **1788.6** | **903** |

裸 store 的 7.6 cyc **与本地完全相同** ⇒ 远端写是真正的 fire-and-forget。
而 `threadfence_system` 后的 1788.6 − 7.6 = **1781 cyc 就是写确认往返**。

### fence 是「一次性排空」，不是「逐个等 ACK」

`nv19` 先发 K 个远端 store 再 fence：

| in-flight K | `__threadfence_system()` cyc（远端） | 本地对照 |
|---|---|---|
| 0 | 1161 | 1161 |
| 1 | 1756（**+595**） | 1161 |
| 64 | 1795（再 +39） | **1161（纹丝不动）** |

- K=0→64 总增量仅 **634 cyc**，而「串行等每个 ACK」的预期是 64×1580 = 101 120 cyc，**实测/预期 = 0.63%**。
- K=0→1 一次性跳升 **595 cyc**（≈一次远端 ACK 往返），此后平均每多一个 in-flight 写只 **+0.6 cyc**。
- 本地对照组恒为 1161 纹丝不动，所以这 +634 cyc **可完整归因于跨 NVLink 的写确认**。

⇒ **64 个远端 store 是完全流水并行发出的，fence 只等最后一个到达并排空写队列。**

### fence 代价的三级阶梯

| scope | cycles | ns |
|---|---|---|
| CTA (`membar.cta` / `__threadfence_block`) | **12** | 6.1 |
| GPU (`membar.gl` / `__threadfence`) | **275.5** | 139.2 |
| SYS (`membar.sys` / `__threadfence_system`) | **1166.5** | 589.2 |

同一 scope 下 `membar.*`、`fence.acq_rel.*`、`fence.sc.*` 和 CUDA 内建函数的数字相差 **<0.3 cyc**
（sys 级：1166.54 / 1166.81 / 1166.54 / 1166.57）——**`fence.sc` 并不比 `fence.acq_rel` 贵**，
编译器把它们降级到了同一条 SASS 指令。

`st.release.sys` 与 `st.global + membar.sys` 也**硬件等价**（1775.5 vs 1793.9，差 1.0%）。

> **可操作结论**：`st.release.gpu`（583.2 cyc）→ `st.release.sys`（1775.5 cyc）要多付 **+1192 cyc = +602 ns**。
> 若通信双方都是 GPU、没有 CPU 或第三方参与，**一律用 `.gpu` scope**，能省 3 倍。

### 没有跨 NVLink 的 write-combining

写后读同地址 1629.0 cyc vs 写后读异地址 1598.0 cyc——**同地址反而略慢 31 cyc**。
若存在 store buffer 转发，同地址应显著更快。符号相反且幅度仅 1.9%，属噪声。
**结论：不存在跨 NVLink 的 store forwarding / write combining。**

## F8 内存序与跨 GPU 同步

### 960 万次 MP litmus，零违例——但这是个弱结论

`nv24` 做了经典的 message-passing litmus：GPU0 写 `data=42` 再写 `flag=1`，
GPU1 自旋等 `flag==1` 后读 `data`，读到非 42 就是观察到了 store-store 重排。

构造上的两个关键点（不做就是假阴性）：
**`data` 和 `flag` 分处不同的 128 B cache line**（中间垫 31 个 uint）；
**每次迭代用全新 slot 且每轮 memset 清零**（复用 slot 的话上一轮残留的 42 会让违例永远看不到）。
slot 放在 **GPU1 显存**，让 writer 的两次写都过 NVLink——这是最容易暴露重排的方向。

| 写侧 / 读侧 | 观测数 | **违例** | 超时 | **写 cyc/it** | 读 cyc/it |
|---|---|---|---|---|---|
| relaxed st / relaxed ld | 1 200 000 | **0** | 0 | **13.7** | 864.7 |
| relaxed st / acquire ld | 1 200 000 | **0** | 0 | 13.6 | 872.3 |
| `fence.sys` / relaxed ld | 1 200 000 | **0** | 0 | **1902.9** | 1903.7 |
| `release.sys` / relaxed ld | 1 200 000 | **0** | 0 | **1898.0** | 1898.8 |
| `release.sys` / acquire ld | 1 200 000 | **0** | 0 | 1899.2 | 1899.9 |
| volatile / relaxed ld | 1 200 000 | **0** | 0 | 13.6 | 864.4 |

8 个组合共 **960 万次观测，零违例，零超时**（超时全 0 很重要——说明不存在「因为超时跳过所以没看到」的假阴性）。
独立的 store-store 观察同样 0 次。违例率上界 **< 8.3e−7**。

> **但零违例的真正原因不是硬件保证有序，而是读侧太慢掩盖了窗口。**
> 看第一行的两个数字：**写侧 relaxed 只要 13.7 cyc/it，读侧要 864.7 cyc/it，慢 63×**。
> writer 早就把 data 和 flag 都发出去了，reader 才刚开始轮询。
> 重排窗口远小于 reader 的检测粒度，所以不可观测。
> 这**不能**证明硬件不会重排。要真正逼出违例需要让两次写落到明确不同的 link
> （利用 `nv32` 的 256 B 条带）、并把 reader 轮询粒度压到几十 cycle——本次没做到。

### 正确性的价格：写侧 139×

1. **`fence.sys` / `release.sys` 把写侧从 13.7 cyc 拉到 ~1900 cyc，慢 139×。**
   这 1900 cyc 与 `nv20` 的 `red + fence.sys` 远端 1758.9 cyc、`atom` 远端 1705 cyc 高度吻合
   ⇒ **fence 的作用就是把「posted 的写」变成「必须等确认的写」，代价正好是一个完整跨卡往返。**
2. **`fence.sys` 与 `st.release.sys` 价格几乎相同**（1902.9 vs 1898.0，差 0.26%）
   ⇒ **优先选 release**：价格一样但语义更精确（只约束这一个 flag），
   有多个独立 flag 时编译器和硬件有更多空间。没有理由用更粗的 `__threadfence_system()`。
3. **读侧 acquire 相对 relaxed 只贵 7.6 cyc（+0.9%），几乎免费** ⇒ **读侧无条件用 `ld.acquire.sys`**。
4. **`volatile` 与 relaxed 完全等价**（13.6 vs 13.7 cyc，都是 0 违例）
   ⇒ **`volatile` 不提供任何跨 GPU 序保证**，它只阻止编译器优化掉访存，不生成任何 fence 指令。
   **不能用 `volatile` 做跨 GPU 同步**——这是个常见误用，这里给了明确否定。

### 一次跨 GPU ping-pong 的硬地板 = 2671 ns

`nv23` 让 GPU0 `k_ping<<<1,1>>>`、GPU1 `k_pong<<<1,1>>>` 用一对 flag 对拍
（`st.release.sys` 置位 + `ld.acquire.sys` 自旋，N=20000 次）。
自旋有 `SPIN_MAX=2e8` 上限、先 launch 消费者、先小迭代 smoke test——实测 0 次超时。

| flag 放置 (f0 / f1) | RTT cyc | **RTT ns** |
|---|---|---|
| 都在 GPU0 | 6251.1 | 3157.1 |
| 都在 GPU1 | 6317.5 | 3190.6 |
| **各写对端、各读本地** | **5288.7** | **2671.1** |
| 各写本地、各读对端 | 6242.6 | 3152.8 |
| host pinned | 8758.6 | 4423.5 |

1. **硬地板 2671 ns。** 对照 `nv20` 的单次远端往返 861 ns：一次 ping-pong 逻辑上是
   2 个单向传播 ≈ 861 ns，实测多出的 **1810 ns 是自旋检测开销**——
   轮询侧不是数据一到就发现，而是要等当前那次 `ld.acquire.sys` 返回才能发起下一次。
   **同步延迟 ≈ 2×传播 + 2×轮询粒度。**
2. **最优放置是「各写对端、各读本地」，快 1.18×。**
   因为这样自旋轮询命中的是**本地**显存（便宜），置位是远端写（posted，不用等）。
   其余三种至少有一侧要远端轮询，每次付 826 ns。
   > **给 NCCL 类库的直接建议：同步 flag 放在读它的那一侧，写方远程写过去。**
3. **host pinned 做 flag 慢 1.66×**（4423.5 vs 2671.1）
   ⇒ **有 NVLink 的拓扑上没有任何理由把同步 flag 放 host 内存。**
4. **payload 传输与同步是串行叠加、没有重叠的**：增量 ns 随 payload 严格线性
   （64 B → 591 ns，65536 B → 312401 ns）。`__threadfence_system()` 强制 payload 先落地。
5. **单线程搬 payload 只有 0.2 GB/s，是峰值的 1/1850**
   ⇒ **同步可以用单线程 kernel，搬数据必须开满线程。**
6. **第一个字节最贵**：0→64 B 边际代价 591 ns（≈一次单向传播），之后每 64 B 只加约 30 ns。
   小消息同步的成本几乎全是固定开销。

### 由此推算：chunk 要 ≥ 8 MB 同步开销才降到 10% 以下

`nv25`（生产者-消费者流水线）**未执行**——时间预算用在了 `nv20`/`nv21` 的两次关键返工上
（详见 F14）。但用上面的实测数字可以推算同步开销占比：

| chunk | 传输时间 ns @370 GB/s | 同步占比（2671 ns ping-pong） | 下界（959 ns 单向 release） |
|---|---|---|---|
| 4 KB | 11.1 | **99.6%** | 98.9% |
| 64 KB | 177 | **93.8%** | 84.4% |
| 1 MB | 2834 | **48.5%** | 25.3% |
| 16 MB | 45350 | **5.6%** | 2.1% |

⇒ **要把同步开销压到 10% 以下，chunk 必须 ≥ 约 8 MB。**
4 KB / 64 KB 的细粒度跨 GPU 流水线几乎全是同步开销。
每 4 个 chunk 同步一次可摊薄 4 倍，把 1 MB chunk 的开销从 48.5% 降到约 19%。

> ⚠ **这张表是推算不是实测**，标注在此以免与其它实测数字混淆。
> 假设 (a) 传输能跑满 370 GB/s、(b) 同步与传输不重叠。
> `nv23` B 段实测支持 (b)，但 (a) 在带背压的双缓冲下不一定成立，真实值会更差。

## F9 原子操作：在远端 L2 就地执行，且是流水化的

### 判决实验：线上字节严格正比于原子次数

有两个互斥假说必须先分清：

- **H_local**：把 cache line 拉到本地 L2 独占，在本地做 RMW。
  特征是**线上流量与原子次数 N 无关**（只有最初一次 fetch + 最后一次 writeback）。
- **H_remote**：请求包发到远端 L2 就地 RMW。特征是**线上流量严格正比于 N**。

`nv22` 把 iter 从 500 扫到 4000（总 ops 39.9 M → 319.5 M，8 倍），同时抓两端计数器：

| case | Mops | GPU0 dTx MB | GPU0 dRx MB | **B/op Tx** | **B/op Rx** | GPU1 dRx MB |
|---|---|---|---|---|---|---|
| atom it=500 | 39.9 | 20.0 | 20.0 | 0.50 | 0.50 | 20.0 |
| atom it=1000 | 79.9 | 39.9 | 39.9 | 0.50 | 0.50 | 39.9 |
| atom it=2000 | 159.7 | 79.9 | 79.9 | 0.50 | 0.50 | 79.9 |
| atom it=4000 | 319.5 | 159.7 | 159.7 | 0.50 | 0.50 | 159.7 |
| **red it=4000** | 319.5 | 159.7 | **0.0** | 0.50 | **0.00** | 159.7 |

1. **ops 涨 8 倍，`dataTx` 同步涨 8 倍，`B/op` 四行完全相同 ⇒ H_local 被彻底排除。**
   3.2 亿次原子，**每一次都真实地过了一趟线**。
2. **噪声底为零**：同样跑 159.7 M 次**本地** atomic，GPU0 的 dTx/dRx 都是 **0.0 MB**。
   而且 GPU0 的 Tx 与 GPU1 的 Rx 在所有行**逐位相等**，双向交叉验证一致。
3. **`red` 的回程流量精确为 0** ⇒ 直接证明 `atom` 的 Rx 流量 **100% 是「送回旧值」的响应包**。

### 单次远端原子的线上成本 = 16 B 请求 + 16 B 响应

让每个 lane 打自己独占的 128 B line（无任何聚合）时，`nv22` 测到
**B/op Tx = 16.00，B/op Rx = 16.00**，精确到小数点后两位。

> **一个 4 B 的 `atomicAdd`，线上要付 32 B，协议放大 8×。用 `red` 可以砍掉一半。**

单地址场景下 B/op 掉到 0.50，而 **16.00 / 0.50 = 32.0 = warp 宽度**——
这是 **32:1 intra-warp 原子聚合**的直接证据，与 `nv21` 用到的聚合修正系数完全吻合。

### 延迟：往返 861 ns，但 97% 是在等返回值

`nv20` 用一条不透明的 inline PTX（`and.b32 %0,%1,%2`，mask 运行时传 0）
构造真依赖链，强制串行（第一版写 `dep = r & 0` 被 ptxas 常量折叠，本地远端都测成 46 cyc）：

| 操作 | 本地 cyc | 远端 cyc | 远端 ns |
|---|---|---|---|
| `atom.gpu.add.u32` | 531.1 | **1705.2** | **861.2** |
| `atom.gpu.cas.b32` | 532.5 | 1706.7 | 862.0 |
| `atom.gpu.add.f64` | 532.2 | 1706.9 | 862.1 |
| `atom.sys.add.u32` | 531.3 | 1705.9 | 861.6 |
| **`red.gpu.add.u32`**（无返回值） | **46.0** | **46.1** | **23.3** |
| `red.gpu.add.u32 + fence.sys` | 585.4 | 1758.9 | 888.3 |
| `ld.volatile.u32`（纯读对照） | 288.7 | 1635.4 | 825.9 |

1. **写类原子在 NVLink 上是完全 posted 的**：`red` 远端 46.1 vs 本地 46.0，**远/本 = 1.00**，
   861 ns 的往返完全看不见。
   `atom − red = 1659 cyc = 838 ns` **就是「等返回值」的纯代价，占 atom 总延迟的 97%**。
2. 加上 `membar.sys` 后 `red` 变成 1758.9 cyc，回到 `atom` 的量级
   ⇒ 那 46 cyc 只是**入队时间**，真正完成仍要 ~1700 cyc，只是线程不必等。
3. **op 类型和数据宽度对延迟零影响**：add/exch/cas/min/and 五种全落在 1704.3–1706.7 cyc
   （极差 2.4 cyc = 0.14%）；u32/u64/f32/f64 全落在 1705.1–1706.9。
   ⇒ **延迟 100% 由链路往返决定，远端 L2 的原子 ALU 相对链路延迟 <3 cyc 可忽略。**
   **跨卡场景下 64-bit 原子不比 32-bit 贵。**
4. **`.sys` scope 相对 `.gpu` 零额外代价**（1705.9 vs 1705.2，差 0.7 cyc），
   连 `release`/`acquire` 版本也一样。因为远端访问本来就绕过本地缓存，`.sys` 的效果是免费附带的。
   **这和 F7 里 store 的结论正好相反**（store 从 `.gpu` 到 `.sys` 要多付 1192 cyc）——
   写跨卡同步代码时，**原子直接用 `.sys` 不要省，普通 store 才需要精打细算 scope**。

### 吞吐：6.6 Gops/s 上限，只占链路 7%

`nv21` 用 159744 线程扫目标地址数 NSLOT。
（踩坑记录：第一版 `tid % nslot` 让一个 warp 的 32 个 lane 全打同一 slot，
被 intra-warp 聚合掩盖成「本地远端完全相同」；改成 `(lane + warp*32) % nslot` 才打散。）

| NSLOT | 本地 atom Mops/s | 远端 atom Mops/s | 本/远 |
|---|---|---|---|
| 32 | 10476.5 | 2947.7 | 3.55 |
| 128 | 26711.6 | 5796.9 | 4.61 |
| 65536 | 75345.0 | 6502.5 | 11.59 |
| 1048576 | 75374.6 | **6601.4** | **11.42** |

1. **满竞争（单地址）时每次 L2 原子只要 86.8 ns，而单次往返是 861 ns**
   ⇒ **861 / 86.8 = 9.9×，同一时刻链路上至少有 ~10 个原子请求在飞。原子是流水化的。**
   （注意：光凭这一点还不能区分流水发生在本地还是远端，定案的是上面 `nv22` 的计数器。）
2. **远端原子吞吐硬上限 6.6 Gops/s，只有本地的 1/11.4。**
   NSLOT 从 128 起就基本饱和 ⇒ 瓶颈从「同地址串行化」切换成了「链路/远端 L2 原子单元总吞吐」。
3. **6.6 Gops × 4 B = 26.4 GB/s，只有 370 GB/s 的 7.1%**（按 16 B/op 的占用口径算是 105.6 GB/s，28%）。
   > **跨卡 all-reduce 绝不能用逐元素远端原子实现，会浪费 93% 的链路带宽。**
4. **把多个 slot 挤进同一条 line 反而快 7.4×**：slot 间隔 4 B 时 NSLOT=1M 拿到
   **48662.9 Mops/s**（194.7 GB/s，达基线 53%），而间隔 128 B 只有 6601.4。
   因为一个 warp 的 32 个 lane 落在连续 128 B 内可以合并成一个 line 事务，
   在远端 L2 一次性对 32 个不同 dword 做原子。
   > **实用优化：远端原子的目标地址要按 warp 连续排布，能拿 7× 吞吐。**
5. **高竞争下 `red` 和 `atom` 吞吐完全相同**（2947.7 vs 2948.0；6601.4 vs 6592.0）。
   `red` 的优势是**延迟**（线程不用等），不是吞吐——远端瓶颈是请求通道本身。

### 为什么原子这么贵：它不能被合并

`nv22` 的附带发现最能说明问题：远端 `st32` 打同一地址 159.7 M 次只用了 **0.19 ms**
（比 atom 的 13.74 ms 快 **72×**），线上流量仅 **0.1 MB**。
连续写同一地址被 SM/L2 彻底合并掉了，只有最后一个值需要过线。
**原子不享受这个优化——每次 RMW 的中间结果语义上都可能被观察到，不允许合并。**
这就是原子相对普通写的根本成本来源。

协议效率上原子也是三类流量里最差的：`nv06` 测得 `raw/data = 2.277`
（对比 STORE 2.039、LOAD 1.990）——4 B 净荷要配一整个包头。

## F10 虚拟通道：不存在，只有带宽竞争

这是用户点名要的实验，`nv26` 的关键设计是**把「带宽竞争」和「队列/VC 竞争」分开**：
先把两条流各压到只用 30% 带宽再做并发。若此时仍互相拖累，才是队列/VC 结构性冲突。

**30% 负载下的跨类型干扰矩阵**：6 个组合的比值**全部落在 0.98–1.00**，
聚合带宽等于两者之和（STORE+ATOMIC = 203 ≈ 103.8 + 103.6）。

⇒ **链路只用 60% 时零干扰，不存在跨流量类型的共享队列/VC 瓶颈。**
「atomic 和 store 共用 VC」的假设被直接否定。

**全速下的表现**（此时纯粹是带宽竞争）：

| 组合 | 各自份额 |
|---|---|
| STORE + STORE | 0.50 / 0.50（185 + 185 = 370） |
| ATOMIC + ATOMIC | 0.50 / 0.50（162 + 162 = 324） |
| **STORE + ATOMIC** | **0.77 / 0.24**（287 / 75） |

同类流量并发时分配**完全公平**（方差 <1%）⇒ 注入端是公平轮转仲裁。
但 STORE 对 ATOMIC 有强烈不对称压制——同样组合在 30% 负载下却是 (1.00, 1.00)。
所以这不是优先级问题，而是 **仲裁按请求数而非按字节**：
store 每个请求携带 16 B 净荷，atomic 只有 4 B，链路满载时 atomic 自然吃亏。

另一个重要观察：**STORE 是 fire-and-forget，1 warp/SM（全卡 78 warp）就能饱和 367 GB/s**；
而 **LOAD 严格受在途请求数限制**，带宽随活跃 warp 数近似线性（44→88→127→157→218→285，1w→8w 增益 6.5×）。
这解释了为什么 LOAD solo 只有 285 GB/s 而 STORE 有 370——**读是被并发度卡住的，不是被链路带宽卡住的**。

## F11 全双工与读写混合

| 场景 | 总带宽 GB/s | 相对单向 |
|---|---|---|
| 单向写 | 370.6 | 1.00× |
| **双向对打**（0→1 与 1→0 同时纯写） | **730.9** | **1.97×** |
| 同时读写（GPU0 既读又写 GPU1） | 593.1（写 349.3 / 读 243.8） | 1.32× |
| 50/50 读写混合 | **451.4** | 1.22× |

1. **链路是全双工，两个物理方向各自独立满速**：双向对打 730.9 = 1.97×，
   两方向分别拿到 365.4 / 366.3 GB/s，**不对称度仅 0.2%**。
2. **「同时读写」只有 1.32× 而非 2×，因为远端读要双向占用**：
   读的**请求包必须从 GPU0 的 Tx 方向发出**，数据才从 Rx 回来。
   所以读和写在 Tx 方向上直接竞争；而双向对打时两边都是纯写，各自只用自己的 Tx。
3. **50/50 混合是最优点（451.4 GB/s，比纯写高 22%）**，混合本身**没有额外惩罚**（没有任何比例低于 0.99×）。
4. 计数器证实两方向同时满载：同时读写时 `dataTx` 和 `dataRx` **都是 6442.5 MB**，完全相等。
5. **双工工作时协议效率反而变好**：`raw/data` 从只写的 2.039 降到同时读写的 **1.667**。
   原因是单向传输时反向链路仍要发流控 flit 和 ACK（只写场景 `rawRx=5840 MB` 而 `dataRx=0`，这 5.8 GB 全是纯开销），
   双向跑时这些控制流量可以**搭载（piggyback）在反向数据包里**，摊薄了开销。

## F12 一对多与多对一：370 GB/s 是全卡共享的，与对端数量无关

### 18 条 link 是共享聚合出口，不按目标静态划分

`nv28` 让 GPU0 同时写 GPU1/GPU2/GPU3，两种发起方式互为对照：

| 目标数 | 多 stream 墙钟聚合 | **单 kernel（block 轮转）** | 份额 std |
|---|---|---|---|
| 1 | 370.4 | **370.6** | 0.0% |
| 2 | 369.8 | **368.3** | 5.7% |
| 3 | 369.4 | **369.5** | 14.3% |

**打 1/2/3 个目标，总带宽落在 0.6% 的带内。** 若 18 条 link 按目标静态划分，
3 目标总和应达 ~1110 GB/s——**被明确否定**。
且**单目标就能吃满全部 18 条 link**（370.4 = 3 目标总和），
不存在「一个 peer 只能用 6 条 link」这类绑定（6×26.562 = 159 < 370，反推可靠）。

⇒ **370 GB/s 的瓶颈在 GPU0 的注入端，不在 link 数也不在 NVSwitch。**
目标数从 1 变到 3 意味着流量分散到 3 组不同的 switch 出口路径，若瓶颈在 switch 总带宽应上升；实测纹丝不动。
计数器 `raw/data ≈ 2.04` 三行几乎相同 ⇒ 协议开销也与目标数无关。

> ⚠ **多 GPU 并发计时的坑**：`nv28` 里「各流之和」列是 392.0 / 419.0，看起来超过了 370。
> 这是假象——各流用自己的 event 计时，而先结束的流在剩余时间里没有竞争，导致单流带宽被高估。
> **必须用墙钟口径（总字节 / max 时间）**，该列恒为 ~370。

### 多对一（incast）：377 GB/s，无崩溃，公平性近乎完美

`nv29` 反过来让 GPU1/2/3 同时写 GPU0（各写一块不相交的 256 MB）：

| 源数 | 各源 GB/s | **墙钟聚合** | vs 单源 | 份额 std |
|---|---|---|---|---|
| 1 | 370.5 | **370.5** | 1.00× | 0.0% |
| 2 | 188.2 / 188.0 | **375.9** | 1.01× | **0.1%** |
| 3 | 125.9 / 125.6 / 125.6 | **376.7** | 1.02× | **0.1%** |

1. **接收端上限 ≈ 377 GB/s，与发送端注入上限基本相同，收发对称。**
2. **不存在拥塞崩溃**：3 源打 1 时总带宽 376.7 ≥ 单源 370.5，甚至微升 2%。
   credit-based 链路级流控在**源端**就把速率压住了（每源精确降到 125.6 ≈ 377/3），
   拥塞被反压到发送方而不是在交换网内丢包重传——与以太网 incast 的典型崩溃行为形成鲜明对比。
3. **【本章最有信息量的一条对照】接收端硬件仲裁比发送端软件调度公平 143 倍**：
   同样是 3 条流分 370 GB/s，incast 份额 std 只有 **0.1%**（125.9/125.6/125.6），
   而 `nv28` 一对多多 stream 高达 **14.3%**（167.8 vs 123.1，相差 36%）。
   差别在于 incast 的仲裁发生在 GPU0 的**硬件接收端口**（严格轮转），
   而一对多的分配取决于 GPU0 上 **SM 的 block 调度顺序**（软件、非确定）。
   决定性佐证：`nv28` 的**单 kernel block 轮转版本没有这个不公平**。
   ⇒ **NVLink 硬件仲裁本身是公平的，不公平全部来自 SM 侧的发起端。**
4. **满载不会淹没小请求**：GPU1 以 370 GB/s 满速灌 GPU0 时，
   GPU2 的单线程探针往返只从 1354 ns 涨到 1405 ns，**仅 +4%（+51 ns）**。
   ⇒ 接收端队列很浅或小请求有独立通道，与 `nv26`「无共享队列瓶颈」一致。

## F13 远端写会偷走接收端 0.85× 的本地 HBM 带宽（且不可缓解）

远端写最终要落到 GPU1 的存储层次里。`nv30` 用 **512 MB buffer**（远大于 60 MB L2，
保证真打到 HBM）做二维扫描：GPU1 跑本地读写混合，GPU0 同时用 NVLink 写 GPU1 的另一块独立 buffer。

**(a) GPU1 本地 HBM 带宽 GB/s**（行 = NVLink 强度，列 = 本地强度）：

| NVL\本地 | 1/8 | 1/4 | 1/2 | full |
|---|---|---|---|---|
| **0 (off)** | 719 | 1246 | 2090 | **2938** |
| 1/8 | 662 | 1147 | 1939 | **2633** |
| 1/4 | 661 | 1145 | 1930 | **2622** |
| 1/2 | 660 | 1142 | 1931 | **2622** |
| full | 660 | 1144 | 1932 | **2625** |

**(b) NVLink 带宽 GB/s**（同样的 16 格）：**全部落在 365–371**，与单独跑时完全一致。

1. **远端写基本完全穿透到 HBM，代价系数 = 0.85**（四档实测 0.83/0.85/0.86/0.85，波动 <4%）：
   370 GB/s 的 NVLink 入流量稳定吃掉 GPU1 约 **313–317 GB/s** 的本地 HBM 带宽。
   **「远端写被 L2 吸收」被明确否定**——若被吸收，本地损失应接近 0。
2. **那缺的 15%（57 GB/s）是被 L2 吸收的**：远端写是 16 B 对齐的整行写，
   L2 可以直接分配行并合并，无需 read-modify-write 回 HBM；
   加上 512 MB 工作集在 60 MB L2 上约 12% 的驻留率。
3. **干扰是一次性阶跃而不是随强度递增**（2938 → 2633 → 2622 → 2622 → 2625）。
   注意这**不是「干扰饱和」，而是自变量没真正变化**：store 是 fire-and-forget，
   1/8 档（39 block）就已经把链路灌到 365 GB/s，四档的实际入流量几乎相同。
4. **【最重要的结构发现】不对称：远端流量伤害本地，本地流量完全伤害不到远端。**
   (b) 表 16 格损失为 0——即使 GPU1 本地正以 2942 GB/s 满速跑，NVLink 入流量依然拿满 370。
   ⇒ **NVLink 入流量在 GPU1 内存子系统里享有实质上的高优先级，本地访存挤不掉它。**

> **对 overlap 规划的直接含义**：通信-计算重叠时，
> **必须给接收端 GPU 的本地带宽打 0.85×NVLink带宽 的折扣**，
> 而且**无法通过降低本地访存优先级来缓解**（方向是单向的）。
> 例：接收 370 GB/s 时，那张卡可用的本地 HBM 从 2938 掉到 2625，**只剩 89%**。

## F14 Copy Engine vs SM 拷贝：CE 全尺寸段完胜，且几乎不偷 SM

`cudaDevAttrAsyncEngineCount` 报告 GPU0/GPU1 各有 **3 个异步引擎**。`nv31` 全面对比两条路径：

| 大小 | **CE GB/s** | SM GB/s | CE µs | SM µs |
|---|---|---|---|---|
| 4 KB | **2.2** | 1.6 | 1.88 | 2.51 |
| 64 KB | **34.7** | 24.1 | 1.89 | 2.72 |
| 1 MB | **216.1** | 190.2 | 4.85 | 5.51 |
| 16 MB | **367.8** | 354.4 | 45.62 | 47.34 |
| 512 MB | **396.5** | 368.6 | 1354.1 | 1456.5 |

1. **不存在 CE/SM 交叉点——CE 在全部 10 个 size 档位上都赢**，这与常见预期相反。
   原因是 **SM kernel 的 launch 开销（~2.5 µs）本身就大于 `cudaMemcpyPeerAsync` 的 1.89 µs**，
   所以小包段 CE 反而更有优势。
   > **GPU-to-GPU 拷贝在任何尺寸下都应优先用 CE**，除非需要在拷贝途中做计算融合。
2. **固定启动开销 = 1.89 µs，64 KB 以内「传输免费」**：
   4 B / 256 B / 4 KB / 64 KB 四档耗时完全相同（1.88–1.89 µs）。
   1 MB 时 4.85 µs ≈ 1.89 + 1 MB/396 GB/s(2.65)，吻合。
   （0 字节仅 0.03 µs 是驱动短路返回，不代表真实提交开销。）
3. **多 CE 并发无任何增益**：1→8 个 stream 各拷贝不相交区域，总带宽恒为 389–391 GB/s（1.00×）。
   ⇒ `asyncEngineCount=3` 的实际含义是「可同时服务 3 个**不同方向**的传输」（H2D/D2H/P2P 并行），
   **不是「P2P 带宽可 ×3」。单向 P2P 场景下开多 stream 做 memcpyPeer 是无效优化。**
4. **CE 零 SM 占用基本成立**：并发跑一个纯 FMA 计算 kernel，
   `+CE 拷贝` 时计算慢 **1.009×**，而**对照组 `+SM 拷贝` 慢 1.070×**。
   这个对照证明测量方法确实能捕捉 SM 竞争，因此 CE 的 ≤1% 是真实但极小的信号
   （可能来自 L2 端口竞争而非 SM 占用）。
   ⇒ **CE 相比 SM 拷贝为计算 kernel 省下约 6 个百分点，同时还多跑了 390 GB/s 的拷贝。**
5. **CE + SM 同打一条链路反而更慢**：合计 384.1 < CE 单独的 395.3（净损失 2.8%），
   份额 CE 55% / SM 45%。**不要为了「榨干带宽」而同时用两条路径。**

> ⚠ **一条需要修正前文的发现**：CE 峰值 396.5 GB/s **高于** F1/F12 里 SM 路径的 370 GB/s 上限
> （82.9% vs 77.1% 的线速占比）。
> 所以 `nv28`「370 GB/s 是 GPU0 的注入上限」这句话应限定为 **SM 路径**的上限；
> **CE 路径另有一条更高的通路，上限约 396 GB/s。**

## F15 NVSwitch 里到底做了什么：组播与在网归约

Hopper + NVSwitch 的 multicast object（NVLink SHARP）官方只给 API 不给行为描述。
`nv33` 用「数四张卡各自的线上字节」给出了直接证据。

**`multimem.st` 由 GPU0 发起，逻辑 payload 2147 MB：**

| 负载 | GPU0 Tx | GPU0 Rx | GPU1 Rx | GPU2 Rx | GPU3 Rx |
|---|---|---|---|---|---|
| **`multimem.st` 组播给 4 卡** | **2147 MB** | 2147 MB | 2147 MB | 2147 MB | 2147 MB |
| unicast 手动广播给 3 卡 | **6442 MB** | 0 MB | 2147 MB | 2147 MB | 2147 MB |

1. **复制确实发生在 NVSwitch 内部**。GPU0 只发出 1 份，三个 peer 各收到 1 份。
   对照组 unicast 要发 3 份。**发送侧线上流量降到 1/3。**
2. **发起方自己那一份也走了交换机绕回来**：GPU0 的 Rx 也是 2147 MB。
   数据明明就在本地，副本仍然是从 switch loopback 回来写进本地显存的。
   这解释了组播为什么只到 277 GB/s 而不是 370——GPU0 的链路要同时扛 277 Tx + 277 Rx。

**`multimem.ld_reduce`（4 卡在网求和）：**

| GPU | Tx | Rx |
|---|---|---|
| GPU0（发起方） | 2147 MB | **2147 MB** |
| GPU1 / 2 / 3 | 各 2147 MB | 0 MB |

3. **在网归约是真的在交换机里做加法**：4 张卡各 Tx 一份进 switch，只有发起方 Rx 一份出来。
   若归约在 GPU0 做，GPU0 就得 Rx 3×2147 = 6442 MB。**接收侧线上流量降到 1/3。**
   注意 GPU0 自己也 Tx 了 2147 MB——它本地那份数据同样要送进 switch 参与求和。

**带宽：**

| 操作 | 逻辑 GB/s |
|---|---|
| unicast 写 1 个 peer | 370.5 |
| unicast 广播给 3 个 peer | **120.2** |
| **`multimem.st` 组播给 4 卡** | **277.4**（= 2.31× 加速） |
| `multimem.red` 在网累加（无返回） | 277.3 |
| `multimem.ld_reduce` 在网求和（有返回） | **151.8** |

4. **`ld_reduce` 比 `red` 慢 1.83×，而 `red` 与 `multimem.st` 几乎完全相同（277.3 vs 277.4）**。
   说明交换机里的**加法器不是瓶颈**（否则 `red` 也会慢），慢的是 `ld_reduce` 等归约结果返回的那个往返。
5. **组播最小粒度 = 2 MB**（`cuMulticastGetGranularity`），比一般 VMM 分配粒度大一个量级。
   小于 2 MB 的 buffer 根本用不了组播——**这就是 NCCL 只在大消息上启用 NVLS 算法的硬件原因。**

> **可操作结论**：做 all-reduce 时，reduce-scatter 侧用 `multimem.red`（277 GB/s），
> 不要用 `multimem.ld_reduce`（151.8 GB/s）做 gather 侧。

## F17 对上层软件的可操作结论

1. **保证 warp 内合并，其他都是次要的。** 合并度从 L=1 掉到 L=32，带宽掉 10.24×（370→35 GB/s）。
   这比任何其他优化的影响都大一个数量级。
2. **单次 P2P 传输的地址跨度要 ≥8 KB，最好 ≥128 KB。** 否则 18 条 link 里大部分根本没被点亮
   （4 KB 只用 56%，512 B 只用 11%）。小消息聚合（batching）的收益主要来自这里，不是来自摊薄延迟。
3. **别指望 L2 帮你缓存 peer 数据。** peer 内存只进 L1（256 KB/SM）。
   跨卡访问的数据复用必须在 L1 尺度内规划，或者显式先搬到本地再算。
4. **读比写贵一倍（32 B vs 16 B 粒度），而且读受在途请求数卡脖子。**
   能改成「远端主动写过来」就不要「本地去远端读」——
   store 是 fire-and-forget，1 warp/SM 就能饱和；load 要 8 warp 才到 285 GB/s。
5. **scope 要分类型选，不要一刀切。**
   - **普通 store**：`.gpu` 比 `.sys` 省 1192 cyc = 602 ns（3 倍差距），只有 CPU/第三方设备参与才用 `.sys`（nv19）。
   - **原子**：`.sys` 相对 `.gpu` **只贵 0.7 cyc，直接用 `.sys` 不要省**（nv20）。
   - **同步 flag 的读侧**：`ld.acquire.sys` 比 relaxed 只贵 0.9%，**无条件加上**（nv24）。
   - **同步 flag 的写侧**：`st.release.sys` 比 relaxed 贵 **139×**——这是唯一真正需要精打细算的地方；
     价格与 `fence.sys` 相同但语义更精确，**优先 release 而不是 `__threadfence_system()`**（nv24）。
   - **`volatile` 不提供任何跨 GPU 序保证**，不能拿它当同步原语用（nv24）。
6. **fence 不怕 in-flight 多。** 64 个在途远端写只让 fence 多花 39 cyc。
   放心批量发 store 再一次性 fence，不要一个 store 一个 fence。
7. **双向流量几乎免费。** 全双工 1.97×，而且双向跑时协议效率还更好（raw/data 从 2.039 降到 1.667）。
   通信模式设计成双向对称能白赚一倍带宽。
8. **all-reduce 用 `multimem.red` 而不是 `multimem.ld_reduce`**（277 vs 152 GB/s）。
   消息小于 2 MB 时组播根本用不了，退化到 unicast。
   **绝不要用逐元素远端原子做 all-reduce**：上限 6.6 Gops/s = 26.4 GB/s，浪费 93% 链路带宽（nv21）。
9. **纯搬运一律用 Copy Engine，任何尺寸都是。** CE 峰值 396.5 GB/s 比 SM 路径高 7.6%，
   且在全部 10 个 size 档位上都赢——连 4 KB 也赢，因为 kernel launch（2.5 µs）比
   `cudaMemcpyPeerAsync`（1.89 µs）更贵。CE 还几乎不占 SM（1.009× vs SM 拷贝的 1.070×）。
   但**别开多 stream**：1→8 stream 总带宽恒为 390 GB/s，单向 P2P 下多 CE 无法叠加（nv31）。
10. **通信 kernel 限制在 ≤8 个 SM。** 这是本轮最实用的一条：
    grid=7 就能拿到 95% 带宽且让其他 kernel 的远端访存延迟只涨 1.29×；
    铺满 78 个 SM 只多拿 5% 带宽，却让延迟恶化到 **7.54×**（nv12）。
11. **规划 overlap 时给接收端 GPU 的本地带宽打折。** 远端写完全穿透到目标 HBM，
    代价系数 **0.85**——接收 370 GB/s 时那张卡的可用本地带宽从 2938 掉到 2625。
    而且这是**单向**的：本地流量再重也挤不掉 NVLink 入流量，无法通过调优先级缓解（nv30）。
12. **同步 flag 放在读它的那一侧，写方远程写过去。** 这样自旋轮询命中本地显存，
    ping-pong RTT 从 3157 ns 降到 2671 ns（1.18×）。**永远不要把 flag 放 host pinned**（4424 ns，1.66×）。
13. **跨 GPU 流水线的 chunk 要 ≥ 8 MB。** 单次同步就要 2671 ns，
    4 KB chunk 的同步开销占 99.6%，1 MB 仍占 48.5%。小 chunk 必须每 N 个才同步一次来摊薄。
14. **远端原子的目标地址按 warp 连续排布，能白拿 7.4× 吞吐**（6.6 → 48.7 Gops/s），
    因为一个 warp 的 32 个 lane 落在同一条 128 B line 内可以合并成单个事务（nv21）。
15. **一对多不用手动分配 link。** 18 条 link 是共享聚合出口，打 1 个还是 3 个 peer 总带宽都是 370。
    但**多 stream 分发不公平（std 14.3%）**，要均衡就用单 kernel 内 `blockIdx % np` 轮转（nv28）。

## F18 还没搞清楚的

诚实列出本轮**没能确定**的问题：

1. **link hash 函数的具体形式。** 只知道不是顺序轮转、最低位是 2 路对分。
   要完整解出需要对每个 256 B 块单独打流量，测试量是 18×N 级别，超出本轮时间预算。
2. **「256 B 条带」的等价歧义。** 从外部无法区分「条带粒度 256 B」和
   「粒度 128 B 但相邻两个 128 B 块映射到同一条 link」这两种实现。
3. **Raw 计数器的精确语义。** 只确定它包含 idle 且忙方向饱和在 ~420 GB/s，
   但「420 GB/s 相对 478 GB/s 的那 12%」到底是编码开销、成帧还是计数器本身的计量口径，无法从外部区分。
4. **每包头的确切字节数。** 因为 Raw 含 idle，无法用 `raw/payload` 反推（这是本轮修正的一个方法学错误）。
   要测准需要能读 link 层的包计数器，NVML 不暴露。
5. **credit 的具体组织方式。** Little's Law 给出了在途容量 769.6 KB（≈342 个 128B 请求/link），
   但这个池子是 per-link、per-VC 还是全局共享的，还是分不清。
6. **`nv05` 中 C=8 那一行不符合简单 16 B 量子模型**（`dataTx` 比 C=4 高 1.47× 而非相等），
   推测是 `st64` 相邻线程被 LSU 合并进同一量子，但没有做进一步的构造去证实。
7. **只有 4 张卡。** 组播加速比是否随组大小线性增长（8 卡应为 7×）、
   NVSwitch 在更大规模下的公平性和拥塞行为，都无法验证。
8. **`multimem.ld_reduce` 只测了 `.add.v4.f32`。** 其它 op（min/max）和精度（bf16/f16）
   在交换机 ALU 上的吞吐可能不同。
9. **FIFO 深度无法直接测量（方法论死结）。** `nv13` 的三种构造全部失败：
   让 `clock64` 可信所需的**数据依赖**恰好摧毁了填满缓冲所需的**并发度**——
   store 有并发但不可观测（fire-and-forget，时间戳会跑到真实流量前面，
   算出 3972.6 GB/s 这种超过物理上限的值），load 可观测但被压成串行。
   所以在途容量只能靠 Little's Law 间接给出。**要直测需要硬件性能计数器暴露队列占用，NVML 不提供。**
10. **「零重排违例」是弱结论。** `nv24` 的 960 万次观测 0 违例，
    真实原因是**写侧 13.7 cyc 而读侧 864.7 cyc，慢 63×**，重排窗口远小于检测粒度。
    这**不能**证明硬件不会重排。要真正逼出违例需要让两次写落到明确不同的 link
    （利用 `nv32` 的 256 B 条带）并把轮询粒度压到几十 cycle，本轮没做到。
11. **`nv25` 生产者-消费者流水线未执行**，时间预算用在了 `nv20`/`nv21` 的两次返工上。
    F8 末尾那张同步开销占比表是**用 `nv23` 实测数字推算的**，不是实测。
12. **发起端的本地带宽代价未测出可信值。** `nv30` 第 5 节因对照组 grid 不一致而失效
    （对照组用 full grid、实验组用 1/2 grid，落差主要来自 grid 本身），记为 inconclusive。
13. **CE 路径与 SM 路径的注入上限不同（396.5 vs 370）**，说明两者走的不是同一条通路。
    这条差异是 `nv31` 顺带发现的，没有做专门实验去定位分叉点在哪一级。
14. **`nv30` 只在单一工作点标定了 0.85 的代价系数。** 因为 store 在 1/8 grid（39 block）
    就已经把链路灌满，四档「NVLink 强度」的实际入流量几乎相同，
    **没有拿到低入流量样本**，无法断言代价系数在低负载下仍然线性。
15. **多 CE 叠加只在单向验证过。** 双向或多 peer 场景下 3 个引擎能否叠加未测；
    考虑到 `nv27` 双向可达 731 GB/s，预期双向有增益，但未验证。

## F19 复现

```bash
cd micro_bench/nvlink
make -j                        # 编译全部实验
./runlock.sh ./bin/nv01_topo   # 单个跑（runlock.sh 用 flock 保证 GPU 独占）
make run                       # 串行跑全部，日志落到 raw_logs/
```

**`runlock.sh` 不是可选的**：NVLink 带宽和延迟测量对干扰极其敏感，
任何一个并发进程都会让数据变成噪声。本套实验由 5 个 agent 并行开发，
全靠这把 `flock` 锁串行化 GPU 访问才拿到可重复的数字。

**写这类微基准的额外的坑**（在 Part E 那四个坑之外）：

1. **NVML 计数器要跑够久。** 单次测量的 payload 至少 2 GB / 持续 ≥1 秒，
   否则驱动心跳和其他进程的背景流量会淹没信号。
2. **Raw 计数器含 idle，不能直接反推包头**（见 F0）。
3. **测在途请求数时，编译器会把独立请求重排成依赖链。**
   必须用 inline PTX + `#pragma unroll`，并且用 `cuobjdump -sass | grep -c STG` 确认指令真的生成了。
4. **测延迟时不能在采样循环里写 global。** 采样先存 shared，循环结束一次性写回。
5. **跨 GPU 自旋 kernel 必须加超时。** 自旋计数上限 + 超时退出，否则一次死锁就要重启机器。
6. **多 GPU 并发计时**：每个 device 用自己的 stream 和 event，先全部 launch 再统一同步；
   kernel 要跑 ≥50 ms，否则 launch skew 会污染结果。
